## 2、正常对话与询问链路

命令处理器校验真实根对话、工作区和输入后，调用官方 `agent.followup(createUserMessage(...))`，立即结束命令处理。后续由主 Agent 的真实轮次接管：

1. 缺少需求时调用 `ask_user_question`，在宿主原生询问界面收集回答；信息充分时直接继续。
2. 通过精确引用或当前可见画布确定工作流，读取最新定义，再调用 `visible_workflow_plan`。
3. 预算按「工作区 × 根对话 × 工作流」收集；规划追问通过 `visible_workflow_plan_answer` 延续同一任务。
4. 真实工具状态、回复和官方子 Agent 入口展示运行过程。新建结果或修改提案通过正常对话反馈，画布继续承担查看和审阅。
5. 修改提案必须接受后才写入工作流。后续业务执行仍属于 Graphon，本次没有执行验收工作流。

实机裸命令已经出现原生“你想做什么？”询问，输入不再留在首页等待规划完成。规划运行期间能够打开工作流面板，官方子 Agent 菜单显示实际子任务。截图留在本机：[原生需求询问](../.cache/planning-entry-20261018-live/b1-fix5-native-requirement-question.png)、[真实工具与子 Agent 状态](../.cache/planning-entry-20261018-live/b1-fix5-native-child-progress.png)。没有将内部思考内容伪造为执行日志。

实现来源：[命令入口](../src/host/planning/command.ts)、[Host 指引和工具](../src/host/index.ts)、[Client 同步](../src/client/index.tsx)、[原子文档 13](../doc/workflow-manual/规划引擎/13-前端入口与规划引擎接入.md)。官方依据为本机 rc.2 的 `dsh-command-goal` followup 处理器和 `dsh-agent-loop`；本项目沿用官方创建用户消息、启动真实轮次的机制。

## 3、真实模型场景结果

使用专门的合成工作流 `入口联动验收-20261018`，ID 为 `f090b1e3-92b6-4b45-804d-b629309ac5eb`。对话 A 提供已存在工作流及 12,000 Token 的预算基线；对话 B 为最终 fix5 的新对话，以下三个入口均在 B 中完成。

表 2：入口、预算与保存结果

| 场景 | 实际行为 | 结果 |
|---|---|---|
| 新对话输入 `/dsh-visible-workflows` | 正常进入对话；原生询问需求；读取指定图并调用规划引擎 | ✅；首份语义不符提案拒绝，更正后接受为 v2 |
| 点击“交给 Agent” | 引用与需求进入聊天草稿；发送后真实规划，修改模板标题和欢迎语 | ✅ 接受为 v3 |

| 同对话不重复问预算 | B 的纠正、按钮和自然语言优化均沿用已有答案 | ✅ 三次后续规划均新增 0 次预算询问 |

| 明确修改预算 | 原生询问后调用专属 `visible_workflow_budget`，生成纯预算提案 | ✅ 接受为 v5，12,000 → 20,000 |
| 显示执行过程 | 正常对话展示工具运行状态，官方菜单展示真实规划子 Agent | ✅ 没有独立规划结果卡片 |

一次“预算询问”指一组预算决策问答，其中可包含是否限制、总量、单次额度等字段，不能将字段数量当成多次询问。没有重复询问的结论来自连续 UI 操作观察与作用域账本共同核对；仅凭账本 hash 不变或缺少工具事件不能证明没有询问。

显式预算修改在 B 第 4 轮只调用专属预算工具，没有新增规划任务或子 Agent。接受提案后，保存实体和高级设置均为 20,000，节点、连线、标题、描述与 v4 一致。见[最终设置截图](../.cache/planning-entry-20261018-live/b4-budget-accepted-settings.png)和[纯预算差异核对](../.cache/planning-entry-20261018-live/b4-budget-only-accepted-semantic-check.json)。截图中的主对话文字生成于接受之前，因此仍写着“尚未生效”；最终事实以接受回执和保存实体为准。

## 4、错误、修复和人工审阅

表 3：本轮实际出现的问题

| 问题 | 处理与证据边界 |
|---|---|
| 初期命令直接等待规划，未自然进入主对话 | 改为官方 followup；最终 B 中验证真实轮次、原生询问与正常反馈 |
| 主模型只用文字追问 | fix5 指引要求缺失需求调用 `ask_user_question`；实机确认原生询问出现 |
| 早期规划选到了错误模型来源 | 规划工具冻结实际主请求模型，避免使用过期或未来待选模型 |
| 输入估算重复计算来源元数据、后置技能目录和未及时结算用量 | 单次估算有效模型消息；最外层步骤钩子过滤子 Agent 不适用目录；逐步结算真实 usage。未增加 64,000 规划额度，也未任意缩小字节估算 |
| B 首提案要求改描述，却改了标题 | 主 Agent 识别不符并原生询问；人工拒绝，原图 v1 保持；更正提案只改描述后接受为 v2 |

首个错误提案的结构校验可以通过，但语义不符合请求。因此保留最新定义读取、主 Agent 复核、差异预览与人工接受；不能把此次验收写成“模型每次首次输出都正确”。[首提案核对](../.cache/planning-entry-20261018-live/b1-first-proposal-semantic-mismatch.json)、[更正接受核对](../.cache/planning-entry-20261018-live/b1-corrected-accepted-semantic-check.json)分别保留。

更早的模型来源和预算阻断失败也保留在本机 manifest，未混入最终通过次数。中间阶段曾短暂观察到宿主空白界面，未取得可归因的崩溃日志；最终 B 连续流程未复现，不能据此宣称所有空白页原因均已修复。
