# 1. 结论与定位

**建议以我们的可视化执行工作流为主体，借鉴 DSH Workflow 的任务管理机制，以及 DeepSeek Flow 的文档编辑体验。** 三者面向的核心问题不同，不能仅凭画布上都有 Agent 节点，就认为执行能力相同。

| 对比维度 | 我们：Visible Workflows | DSH Workflow | DeepSeek Flow | 推荐理由与采用边界 |
| --- | --- | --- | --- | --- |
| 核心定位 | ✅ 图形化搭建、执行和排查工作流 | 以代码编排原生子 Agent 的任务执行系统 | 以 Markdown 为核心的可视化流程编辑器 | 针对我们希望保留画布、节点批注并实际运行流程的目标，继续采用我们的产品主线。 |
| 最值得保留或借鉴的部分 | 画布、结构化节点、批注、固定节点、人工介入 | 原生子 Agent、并发控制、预算、运行快照、结果验证 | Markdown 文档、画布同步、文档优化预览、草稿恢复 | 三方优势位于不同层次；后续各表逐项标出推荐来源。 |
| 不应误认为已经具备的能力 | 原生子 Agent 接入仍是建议；尚无完整预算账本与通用断点续跑 | 快照续跑不恢复 JavaScript 调用栈；预算存在未知用量边界 | 画布 Agent、Map Agent 等节点没有独立执行引擎 | 名称、界面和文档中的流程描述不能代替实际执行实现。 |

**标记规则：** ✅ 表示在该项上，更推荐我们采用或借鉴该项目的做法，并非测试通过标识或综合排名。没有 ✅ 的行表示不宜选出单一优胜者，或三者都未提供充分实现。表内的“未见”限于本次检查的版本，不推断未来路线。

## 3.2 执行语义与 Agent 调度

| 对比维度 | 我们：Visible Workflows | DSH Workflow | DeepSeek Flow | 推荐理由与采用边界 |
| --- | --- | --- | --- | --- |
| 完整工作流执行 | ✅ Graphon 驱动结构化节点执行，界面与工具调用使用同一执行体系 | 自有代码工作流引擎，执行脚本和委派任务 | 仅内置布尔逻辑门求值；其他步骤由会话 Agent 按文档执行 | 我们的执行图与产品目标一致。DeepSeek Flow 的 flow_evaluate 明确不执行 Agent、Map Agent 等步骤。 |
| 数据处理与工具节点 | ✅ 20 类节点，包含模板、HTTP、代码、提取、聚合、变量赋值、工具等 | 主要用代码、工具及子 Agent 完成处理 | 节点主要描述步骤，缺少对应的独立执行器 | 常用处理显式节点化，便于配置、追踪输入输出；不把节点数量当成实现质量评分。 |
| 原生子 Agent 集成 | 当前为模型生成—工具调用循环；接入宿主 subagents 尚未实现 | ✅ 实际调用宿主 subagents.start，支持等待、消息、停止与结果获取 | 文档助手和拓扑审查使用子 Agent；不是画布节点执行 | 采用 DSH Workflow 的运行时接法，让我们的 Agent 节点映射原生子任务。三者都有 Agent 相关代码，但用途不同。 |
| 并发、扇出与汇总 | 普通图执行器为单 worker；iteration 内部支持受限并行 | ✅ 并发信号量、parallel、pipeline、synthesize 等任务组合 | Map Agent、Merge 属于流程描述，不等同于实际并发调度 | 拖出多个节点可以表达分工；是否并行、如何限流和取消，要由运行时保证。 |
| 人工介入与等待输入 | ✅ human 节点支持输入、动作、等待、默认值和超时处理 | 可依赖宿主审批与代码逻辑；未见等价的画布 human 表单节点 | 用户可接受文档修改；这不是执行途中的人工节点 | 我们已经把人的介入作为流程语义，应继续保留；并行 iteration 内 human 仍有限制。 |
| 条件判断与布尔逻辑表达 | 有可执行 if 分支，结合上下游数据判断 | 用 JavaScript 条件与控制流表达 | ✅ IF/ELSE、AND、OR、NOT、NAND、NOR、XOR、XNOR，明确真值和目标传播 | 借鉴清晰的逻辑门与谓词表达，再接入我们的实际执行器；不建议只增加图形而缺少执行语义。 |
| 循环与有界迭代 | ✅ iteration、loop、exit_loop 有实际执行逻辑 | 代码循环及任务组合，可自行实现终止条件 | 允许带迭代上限和退出条件的反馈边，但不负责循环步骤执行 | 保留我们的显式循环容器。三方都能“画或写循环”不代表运行保障相同。 |
| 工具权限与执行约束 | 工具目录与节点允许范围约束自有 Agent 循环 | ✅ 原生权限继承、只读工具过滤与任务级约束 | 编辑辅助 Agent 有作用范围和输出约束 | 借鉴 DSH Workflow 的原生任务权限模型，再叠加我们的节点工具白名单；不可因升级为子 Agent 而扩大权限。 |

# 4. 如何结合，避免做成三套相互重叠的系统

## 4.1 保留一套执行图，给 Agent 节点换成原生执行后端

用户仍在我们的画布里添加多个 Agent 节点，通过连线指定输入、依赖和结果去向。节点被调度时，再通过适配层创建 DeepSeekHarness 原生子 Agent，并把工作流运行 ID、节点 ID、迭代执行实例 ID 与宿主子 Agent ID 关联起来。停止、消息、工具权限、过程事件和用量都通过这一层接回画布。

**接入之后，多个 Agent 节点确实可以作为多个子 Agent 协作。** 但这只解决“由谁执行节点”。并发准入、预算分配、完成验证、历史快照和中断恢复仍是工作流级能力，需要另行补齐。主图的单 worker 限制也不会因为换了 Agent API 自动消失。

## 4.2 从 DSH Workflow 借机制，避免再塞入第二套主引擎

保留现有图调度作为唯一的主流程调度器，把原生 Agent 管理、任务准入、预算预留与结算、事件日志、运行快照和结果验证提炼为公共服务。我们的节点执行器调用这些服务，而不是把完整的代码工作流引擎嵌到每个 Agent 节点里，否则取消、重试、预算和状态可能出现两套负责人。

预算建议同时记录“已消耗、已预留、未知用量”，把初次执行和修复追加调用放进同一账本。未知用量不能简单按零归还预算。快照应冻结本次执行图、嵌套依赖与配置；续跑必须检查快照及任务约束是否匹配，明确显示哪些结果复用、哪些任务重做。

## 4.3 从 DeepSeek Flow 借文档体验，避免两个事实来源

为工作流和节点提供可阅读的 Markdown 说明或导出视图，借鉴当前文档优化的“建议—预览—接受”过程，以及草稿和辅助结果的独立保存。结构化图仍是可执行定义；外部 Markdown 修改若要影响执行，应先解析成待确认的图变更，经过版本、类型、固定节点和连线校验再提交。

不要让 Markdown 与图配置分别直接覆盖对方。也不要承诺能把任意 DSH Workflow 脚本或 DeepSeek Flow 文档无损转换成我们的节点图：任意代码、自然语言步骤与确定性节点的表达范围不同，需要明确受支持的导入子集。

## 4.4 三个值得避免的直接照搬

- 不把 DeepSeek Flow 的“整个工作流优化”直接改写模式当成默认：跨节点修改更适合先展示差异，保留固定节点保护。
- 不把 DSH Workflow 的预算和缓存直接宣传成严格限额、任意位置恢复或外部动作仅执行一次。
- 不让切换流程自动继承旧的执行意图。选择当前流程与发起一次运行应有清楚的边界。

# 5. 建议实施顺序与验收标准

| 优先级 | 建议动作 | 主要参考 | 可检查的完成标准 |
| --- | --- | --- | --- |
| P0 | Agent 节点接入宿主原生子 Agent | ✅ DSH Workflow | 画布节点与宿主任务一一关联；等待、停止、错误、权限和过程事件正确回传；现有图与批注能力保持可用。 |
| P0 | 统一运行身份和不可变快照 | ✅ DSH Workflow，扩展到我们的嵌套图 | 图修改后，旧运行仍能准确说明当时执行的定义；嵌套流程不悄悄换成最新版。 |
| P1 | 并发准入与预算账本 | ✅ DSH Workflow 的机制，修正未知用量边界 | 并发任务不能重复占用同一预算；修复调用纳入账本；缺失用量明确标记；取消能释放合适的资源。 |
| P1 | 图修改预览与持久化草稿 | ✅ DeepSeek Flow 的单文档建议模式，保留我们的批注 | 建议未接受不覆盖图；版本冲突可识别；未发送批注和未接受建议重开后可恢复。 |
| P2 | 可审计的续跑与结果验收 | ✅ DSH Workflow | 展示缓存复用原因；失败任务可单独重做；读取或修改证据可追踪；有副作用的未知状态不会盲目自动重试。 |
| P2 | Markdown 说明和有限导入导出 | ✅ DeepSeek Flow | 导出可阅读、可比较；可执行字段与说明字段区分明确；不支持的语义明确提示，不静默丢失。 |

**产品定位建议：面向 DeepSeekHarness 的可视化 Agent 工作流，让用户能够看清流程、批注修改、介入执行，并追踪每个节点的结果。** 我们的差异化可以继续建立在“可见、可改、可干预”上；底层复用宿主原生 Agent，再补充成本控制与可靠恢复。
