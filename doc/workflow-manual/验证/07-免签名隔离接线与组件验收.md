## 1. 已实施的变化

| 部分 | 本轮实现 | 边界 |
| --- | --- | --- |
| 启动顺序 | 新增 `createHostIsolationPrepare`，在真实 Loader 配置树加载前逐项等待可信前置服务，在私有作用域挂载原生进程服务，再安装受限公共接口 | 必须由真实 Host 的早期 prepare 调用；普通 YAML 插件顺序不够 |
| 失败处理 | 前置服务 PENDING、晚加载、清单缺失、准备/清理失败均拒绝启动；异常正文不透传，同一 Context 失败后不能重试 | 不自动生成 Secret 可用证明 |
| Host 控制通道 | 新增 MXC Host 适配器；FD7 入口在受限内层写入固定的控制标记，调用者环境不参与授权；受管执行由 Host 控制超时 | 保留真实 Harness 控制协议，PTY 与完整进程树仍单独验收 |
| MCP | 固定官方 rc.2 客户端源码及 SDK 的实际文件哈希，只替换其私有 transport factory；探测进程和正式进程都通过受管入口 | 保留官方工具、资源、回调和重连实现；没有政策的网络 MCP 拒绝，不回退 |
| MCP 关闭与取消 | 启动/关闭竞态、消息限额、非法帧、服务端回调、取消通知、退出排空和 SDK 探测 sibling 清理已覆盖；不能证明收尾时锁住后续启动 | 原生进程范围退出不是全部后代退出的证明 |
| Graphon 环境 | 从继承宿主环境改为必要 OS 字段白名单、固定 PATH 和私有 HOME/TMP；不继承模型密钥、代理、账号目录和运行时注入变量 | 这是数据通路收紧，不等于 Graphon 已经过完整 OS 隔离 |

另新增 单进程监护研究组件（原路径 `native/process-supervisor/README.md`，已移除），复用固定 MXC 编译策略并追加进程限制。实测发现 `POSIX_SPAWN_SETEXEC | POSIX_SPAWN_SETSID` 可绕过仅禁止 fork/setsid 的策略，因此还必须禁止 `posix_spawn` 系统调用。严格策略只完成了固定原生 worker 的验证；Electron/Node 启动兼容未通过，故组件未打包、未接入当前执行器，不能替代通用 shell、CLI 或 MCP。

## 2. 真实 Harness 组件验证

本轮直接使用 `/Applications/DeepSeek Harness.app` 内的 Node 24.18.1 / Electron 44.0.0，以及已安装的 rc.2 `boot`、Loader、Tools、SystemPrompt、LocalSubprocessRuntime、MCP Client/SDK 和 control helper。合成输入只用于验证协议和拒绝路径；没有创建另一套工作流产品，没有模型调用或凭据操作。

- 启动组件：真实 Loader 在边界 active 后才加载消费者；公共 subprocess 不是私有原生 provider；故意让准备失败时，消费者不执行，真实 boot 清理失败根上下文。
- FD7：真实 `openInheritedControlChannel()` 成功打开并消费标记，控制回复与 stdout 分离；合成凭据环境值未传给子进程。进程树报告仍为 `unverified`，没有把直接进程退出冒充完整树回收。
- MCP：真实插件与 SDK 完成初始化、工具列出/调用、取消通知、服务端 ping、未声明回调拒绝、工具列表变化重注册和卸载清理；分别覆盖协议探测收到不支持响应、探测时服务直接退出的旧服务行为。通过真实 MCP 工具读取，确认工作区合成公开文件可读，隔离目录中的合成文件实际返回 EPERM/EACCES。仅测试本地合成 stdio 服务，网络默认拒绝。
- 单进程监护：8 个场景、12 项原生限制/正向检查通过。正常退出、取消、控制连接断开、guardian/watchdog 崩溃、超时、独立合成 Host 崩溃等情况下，所有本轮合成进程在兜底清理前已退出。限制下无法向沙箱外监护进程发信号或 ptrace；线程、向自身发信号和普通 exec 可用。没有强制造出 PID 重用、内核不可中断状态或两个监护进程同时消失，不宣称通用进程树监督已完成。

所有报告均保持 `secretReady: false` 或等价关闭状态。**尚未进行“录入凭据→合法操作成功→主/子 Agent 读取失败”的最终闭环。**

## 3. 真实 Desktop 接入阻塞

已安装 Desktop 的 `main()` 调用 `runProfile()`；`runProfile()` 在内部创建 `boot(..., prepare, ...)` 的闭包，但没有把可信外部 prepare 透传进去。因此当前 profile 插件无法在文件、子进程、Agent 和 MCP 消费者启动前获得这个入口。

最小上游改动是给 `runProfile` 增加仅供可信启动代码传入的 `prepareHost` 回调，并在现有 `provideCmdline` 之后、加载配置树之前等待它；Desktop 发行入口静态组合本仓库的新模块。详细位置、示意补丁、原行为兼容要求及失败退出要求见 Host 接线说明（原路径 `host-extensions/dsh-secret-isolation/BOOTSTRAP-INTEGRATION.md`，已移除）。这是源码发行改动，不能通过解除应用签名校验代替。

得到入口后，仍须完成可信模块清单在 import 前的检查、重复公共 provider 的移除、CLI/MCP 联网政策、GUI/IPC/调试与插件安装目录保护、所有旧进程清理，以及真实主/子 Agent 验收。单独完成启动 hook 不足以开放 Secret。
