## 4. 实际请求结果的判断

本节记录已完成验收的逐次授权实现：原生组件在用户批准本次请求并认证后读取凭据，自行注入固定请求的 Authorization。它只接收最终状态码，拒绝重定向并取消响应正文交付；调用者不能传入 URL、请求头、请求体或代理设置。第 7 节另列新持久授权的独立实机证据。

| 实际观察 | 可以得出的结论 | 不能得出的结论 |
| --- | --- | --- |
| `status_code:401`，Host `ok:false` | 一次真实请求抵达目标并获得身份拒绝响应；假测试值可以用于此项验证 | 不能称为有效 API 密钥通过认证 |
| `status_code:2xx`，Host `ok:true` | 此次固定请求收到成功状态码 | 不证明任意 API 或所有后续请求均可使用 |
| `invalid_request` | 请求或 Bearer 格式校验失败 | 不证明发出了网络请求 |
| `network_failed` / `network_denied` | 请求失败或被目标、TLS、重定向策略拒绝 | 不证明凭据有效，也不证明请求已获得最终 HTTP 响应 |
| 运行 `completed` 且输出 `401` | 工作流成功交付了业务状态码 | 运行完成不等于凭据认证成功 |

原生协议的 `ok:true` 表示成功取得状态码；Host 随后按状态码生成业务字段 `ok`，因此原生收到 401 后，画布最终应得到 `{ "ok": false, "status_code": 401 }`。两层含义在验收记录中分开写明。

### 4.1 本次真实 HTTP 结果

用户明确确认允许本次固定目标请求并完成系统认证。运行 `3c4e7a6d-4b1f-468a-b13a-44e126c11f5c` 于北京时间 2026-10-17 15:55:11 开始，15:56:29 结束，运行及 HTTP 节点的状态均为 `success`；HTTP data 仅为 `{ "ok": false, "status_code": 401 }`，画布输出为 `401`。

限定字段核对表明：节点输入仅有 `credentialOperation` 的操作 ID 和 Secret 声明 ID；Secret 定义只含 6 个声明字段，运行环境快照没有 Secret 原值，HTTP 结果不含响应正文、响应头或余额。验收工具未读取凭据原值。此结果证明固定请求实际返回了身份拒绝状态，不能写成假测试值通过有效 API 密钥认证。

证据：[真实 HTTP 401 运行摘要](DSH021证据/http-401-run.json)、[用户确认与 Desktop 阶段观察](DSH021证据/desktop-stage-observation.json)。保留运行文件 SHA-256 便于核对，但未复制原始运行文件或会话。

### 7.1 管理窗口与运行协议

当前原生管理窗口只有“仅保存”“保存并授权自动使用”“撤销自动使用”“删除”“关闭”五个动作。打开时一次系统本人认证；“保存并授权自动使用”在同一窗口明确展示并授权固定目标，不要求保存后再开另一个窗口。“仅保存”先撤销旧授权，并为新值生成新的 epoch，即使保存的是同样文本也不沿用旧授权；删除会删除值及授权，保留流程声明。

自动使用授权仅保存在本机 Keychain，绑定本工作流、本变量、凭据 epoch 和固定 `GET https://api.deepseek.com/user/balance` 目标。目标指纹还包含认证方式及仅返回状态码的策略。`status` 只返回 configured/missing 与 authorized/required；`manage` 可返回 saved/authorized/revoked/deleted/unchanged 及授权状态，不返回原值或授权记录。后台 `execute` 不调用 UI 或系统认证，没有有效授权就明确失败；组件 ready 不代替变量授权。完整协议以[现行原生说明](../../../native/os-secret-broker/README.md)为准。

并发撤销与发送边界的原生修复已完成并冻结，原生检查与 Host 完整构建通过，新包已安装。撤销不能追回已经发出的请求，不把源码检查或旧包的逐次认证结果写成新模式的真实并发行为已验收。
