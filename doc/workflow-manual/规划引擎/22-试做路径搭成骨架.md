# 试做路径搭成骨架

核对日期：2026-10-26。对象：v0.0.2 r42（提交 `5bdfc26`）。设计与决定见[设计 26](设计/26-照试做搭骨架.md)。

[规划引擎索引](README.md) · [先执行验证再生成工作流](18-先执行验证再生成工作流.md) · [写出文件反推模板](23-写出文件反推渲染模板.md) · [完整草稿](24-完整草稿的组装与预编译.md) · [试做方法的接收](25-试做方法的直接接收.md)

## 1. 解决什么问题

试做已经用工作流同款工具跑通了“抓取 → 提取 → 写入 → 回读”。但作者模型生成节点图时，仍要重新决定网址、选择器、字段和写入路径。Desktop r32–r34 中，这一步要 4–7.5 分钟，多数时间花在首次输出前的思考上。

骨架的做法是：Host 把试做跑通的调用直接换成对应节点，作为已定事实交给作者，作者只补试做没定下来的部分。2026-10-25 用户决定“按推荐做法来，不用锁死”，所以骨架不锁定：作者可以改，也可以删，但要写明理由。

骨架不降低思考强度，也不改编译器、提交格式和校验，只是作者提示里多了一份输入事实。

## 2. 骨架从哪里来

只读规划上下文里已冻结的试做证据 `context.conversation`，不重新执行，也不读文件。

- 只看 `tool-call` 记录，按记录顺序处理。
- 结果为 `failed` 的调用不进骨架，包括写前探测。
- 同一网页工具连续调用多次，只保留最后一次；前面几次通常是被修正掉的尝试。
- 参数被截断或解析不出 JSON 的网页调用不进骨架，留给作者。
- 写入调用被截断时，从截断文本里找 `file_path`。找不到、但任务只有一个产物时，就用该产物路径。

## 3. 调用怎样换成节点

| 试做调用 | 骨架节点 | 带过去的配置 |
| --- | --- | --- |
| `workflow_http_request` | `http` 节点（key `fetch`） | `url`、`method`、`headers`、`timeoutMs`（限制在 100 ms–120 s）、请求体 |
| `workflow_html_select` | `builtin:html.select` 工具节点（key `select`） | `items`、`fields`、`limit`、`baseUrl`；`html` 接最近 HTTP 节点的 `{{fetch.text}}` |
| `workflow_html_extract_text` | `builtin:html.extract_text` 工具节点（key `extract`） | `html` 接最近 HTTP 节点；状态码和响应头也接 HTTP 节点的输出 |
| `write`（写到 `trialTask.artifacts` 里的产物） | `verified-file-write@1.1.0` 模块（key `save`） | `target` 是产物的工作区相对路径；`content` 暂填 `{{render.text}}` |
| 写入前的 `read`（读 `trialTask.inputs` 里的输入文件） | `native:read` 工具节点（key `read`） | `file_path` |

产物的写前探测和写后回读不另建节点：写入模块自带精确探测、回读和窗口核对，输出 `check` / `checkNote`。写到产物以外的临时文件，以及 bash、web_fetch 等没有对应节点的调用，都不进骨架。

当前工具目录里没有对应的内置工具时（例如没装 `builtin:html.select`），该调用不进骨架，并在 `open` 里注明需另选节点。

## 4. 交给作者的内容

骨架作为 `trialSkeleton` 放进作者首轮提示，与 `procedure`、`trialEvidence` 并列。

| 字段 | 含义 |
| --- | --- |
| `forms` / `modules` | 可以直接放进 create 提交的节点和模块声明 |
| `order` | 建议顺序 |
| `sources` | 每个 key 来自哪条试做证据 |
| `open` | Host 定不下来、留给作者补的部分：开头 input、结尾 output、写入前的整理节点、产物检查 |
| `instruction` | 以骨架为起点；改动或删除骨架节点时，在 assumptions 写「骨架调整：<key>：理由」 |

骨架用到的节点模板（http、HTML 工具、读取工具）随首轮提示一起预取，作者不必再查询模板。

Host 能补齐成完整提交时，提示里改为只给 `draft`，不再重复 `forms` / `modules` / `order`，见[完整草稿](24-完整草稿的组装与预编译.md)。

## 5. 偏离骨架怎样记录

偏离骨架不会被退回修补；退回会多一轮模型调用，违背提速的初衷。发布时，Host 对比骨架和候选图：

- 候选里能找到同类节点，并且关键配置一致（网址；选择器与字段；写入路径），就记为“沿用”。
- 找不到，或关键配置不同，就记为“调整”。assumptions 里写了「骨架调整：<key>：理由」的，带上理由；没写的标为“未说明理由”。
- 把值改成 `{{input.字段}}` 运行参数不算调整，嵌在 `fields` 等对象深处的单个选择器也一样。

对比结果写进发布回执 `verification.trialSkeleton: {used, adjusted, meaning}`，由主 Agent 如实转述。骨架由冻结证据确定性生成，发布时重新计算即可，不单独保存。

## 6. 什么时候没有骨架

- 不是 create（修改、批注不走骨架）。
- 不是来自已验证试做的任务（`source.kind` 不是 `verified-trial`）。
- 规划驱动不是 `template-fill`，或主 Agent 走的是早交接路由。
- 试做调用里没有一条能换成节点。
