# 减少思考量：唯一写法与节点匹配（T21）

## 1、问题

160 次配对实验里，模板组只有在精简组需要先查目录的案例中更快。其余案例和精简组持平，branch 和 large-edit 还更慢。逐请求拆分后：

| 第一个请求（中位数） | 精简组 | 模板组 |
| --- | ---: | ---: |
| 首 Token 等待 | 4.7 s | 4.7 s |
| 输出速度 | 51.4 tok/s | 51.5 tok/s |

两组读输入、出字的速度一样，请求耗时约等于“输出 Token ÷ 51”，而输出里 70%～85% 是思考。**想提速，只能让模型少想。**

2026-10-22 对当前提示词做了 18 次诊断请求，保存了思考原文（`.test-data/thinking-diag/`，不入库）。多出来的思考主要花在三件事上：

- **规则互相冲突。** “新建时默认出口用 result”和“两个分支各有一个输出节点”无法同时满足，模型在 branch 上反复权衡，最多占思考的 38%。
- **同一件事有两种合法写法。** 输入可以写 `{{input.score}}`，也可以写 `{{start.score}}`；模板节点可以直接引用 `{{input.text}}`，也可以先在 `inputs` 里映射成 `{{text}}`。模型要先判断哪种“更对”，large-edit 里有模型在两种写法之间来回改了三次主意。
- **细节一次性全部敲定。** 精简组第一轮只列方案，细节留给查询之后；模板组预取了全部模板，在一次请求里把所有细节都想完。

选节点本身很快，思考原文里通常只有几行。

## 2、原理：思考量取决于要做的选择，而不是信息多少

- **给模型更多信息，它不会因此少想。** 信息越多，看得见的选项越多，要排除的可能也越多。
- **思考量 ≈ 要做的决定数 × 每个决定的合法答案数。** 能确定唯一答案的地方，就不要留给模型判断。
- **这和“让非法状态无法表示”是同一条思路**（设计文档 11 第 8.7 节）：那里由编译器把意图明确的错位直接归位，这里让提示词只教一种写法。编译器仍然接受其他等价写法，只是不再把它们展示给模型。
- **匹配应由 Host 在第一轮请求前完成。** 做成 agent 主动调用的工具，每次调用都要多一轮请求：首 Token 等待约 5 秒，还要重读一遍上下文。精简组第一轮查目录就因此多花约 20 秒。
- **agent 仍然自己设计整张图。** 不提供固定骨架，不按配方限制结构；减少的只是“写法”上的多余选择。

## 3、改法

**第一步：唯一写法（两组共用）**

- 输入字段只教一种引用写法，if 等条件节点的左值也一致；其他写法编译器照常接受。
- 模板节点的取值方式只教一种，另一种只在确有必要的情况下说明用途。
- 出口命名不再冲突：只有一个输出时的约定，与多个分支各有输出时的约定，分别写清楚。
- 系统指令、规则、Schema 描述、运行语义与模板说明中相互重复或矛盾的表述，以同一种写法为准。

**第二步：匹配结果只给本任务需要的内容（模板组）**

- Host 预取到的节点，只附带本任务下的唯一用法，以及完成任务需要的字段说明。
- 与本任务无关的备选写法和通用说明不再随预取发送；完整目录仍可按需查询。

## 4、验证

- 每一步完成后，用同样的 18 次诊断请求对比思考 Token，确认降低后再继续。
- 最后按冻结条件做配对复测，报告两组的绝对思考量、耗时和成功数，以及配对中位比。
- 第一步对两组同时生效，配对比值可能不变；判断效果时要看两组各自的绝对耗时。

## 5、边界

- 思考强度保持 max，不在本任务里按难度调整。
- 不改冻结的实验清单和 `t09-config.json`；复测使用新的输出目录。
- 旧图和已有记录照常可读。

## 6、结果与新学到的原理（2026-10-22）

完整数字见 [T21 证据](../../../../docs/evidence/t21-thinking-20261022/README.md)。

- **唯一写法有效。** 模板组每次尝试都一轮成功、0 次修复，成功设计耗时中位数从 45.6 s 降到 27.1 s。第二轮配对的四项冻结门槛全部满足，中位比 0.870。但自助抽样区间是 0.60—0.99，还不能算稳定达标。
- **减少信息不等于减少思考。** T21.2 删掉重复的说明文字和例子后，请求体小了一半，模型却开始自己读 Schema、逐条自检，思考反而更多，已回退。能减少思考的是**减少要做的选择**；对模型有帮助的确认信息，应该保留。
- **统一写法时，原来靠“写法不同”隐含的边界会消失，必须明说。** 过去模板里用的是局部变量 `{{metadata | tojson}}`，一看就只属于模板节点。统一成 `{{上游.字段}}` 之后，模板节点和输出节点的引用长得一样，模型就把过滤器写进了 output.text。修法有两部分：把边界写成一句明确的话；再加编译检查，让错误在提交时就得到具体修法，而不是到运行时才失败。
- **对两组同时生效的改进，在配对比里看不出来。** 编辑类两组都快了约 40%，比值却仍接近 1。判断产品是否变快，要看两组各自的绝对耗时。
