# 26、照试做搭骨架

## 1、背景与决定

2026-10-25 用户决定：试做跑通的路径由 Host 直接换成对应节点，搭成骨架交给规划模型；模型只补试做没定下来的部分。骨架是“已定好的起点”，不锁死，模型可以改动或删除骨架节点，但要说明理由（用户原话：“按推荐做法来，不用锁死”）。

Desktop r32–r34 观察：试做已经用工作流同款工具跑通了抓取、提取、写入、回读，生成节点图仍要 4–7.5 分钟。耗时主要是模型首次输出前的思考（r34 大页面 258 秒），其中大部分在重新决定试做已经验证过的结构：用哪个节点、网址、选择器、字段、写到哪里。

不降低思考强度（见“不降低思考强度”的既有约束）；只把已确定的结构作为输入事实交给模型。

## 2、骨架从哪里来

只用规划上下文里已经冻结的试做证据 `context.conversation` 中 `kind: tool-call` 的记录，不重新执行、不读取文件。要求：

- 只取 `truncated: false` 且参数能解析为 JSON 对象的调用；截断或解析失败的调用不进骨架，留给模型。
- 结果状态为 `failed` 的调用不进骨架（含写前探测；写入模块自带探测）。
- 按记录顺序排列；同一网页工具连续多次调用时只取最后一次（前面的通常是被修正的尝试）。
- 写入调用的参数被截断时，从截断文本里找 `file_path`；仍找不到且任务只有一个产物时，用该产物路径。

## 3、调用到节点的对应

| 试做调用 | 骨架节点 | 来自调用的配置 |
| --- | --- | --- |
| `workflow_http_request` | `http` 节点 | `url`、`method`、`headers`、`timeoutMs` |
| `workflow_html_select` | `builtin:html.select` 工具节点 | `items`、`fields`、`limit`、`baseUrl`；`html` 接最近的 HTTP 节点 `{{key.text}}` |
| `workflow_html_extract_text` | `builtin:html.extract_text` 工具节点 | `html` 接最近的 HTTP 节点 `{{key.text}}` |
| `workflow_file_stat`（统计输入文件或其他非产物文件） | `builtin:file.stat` 工具节点 | `inputs.path` = 文件的工作区相对路径（绝对路径按输入文件后缀对应）；草稿里与读同一文件的 document 节点共用路径参数；统计产物的调用不进骨架，由写入模块回读负责 |
| 先 `glob`（不传 path，目录写在 pattern 里）列出 ≥2 个文件，再对列出的每个文件都调用一次 `workflow_file_stat`（集合完全相同） | `native:glob` 工具节点 `files` → `list` 节点 `sorted`（按路径升序）→ 迭代 `each`，子链里一个 `builtin:file.stat` 节点 `stat` | `files.inputs.pattern` = 试做的 pattern（草稿里换成参数 `input.pattern`）；`sorted.listSource=files.value.paths`；`each.iterator=sorted.result`、`outputVariable=stat`；`stat.inputs.path={{item}}`。只统计了部分文件、glob 传了 path 时不折叠，仍按上一行逐个固定 |
| `write`（写 trialTask.artifacts 里的产物） | `verified-file-write@1.1.0` 模块 | `target` = 产物的工作区相对路径（绝对路径按产物路径后缀对应）；`content` 暂填 `{{render.text}}` |
| 写入之前的 `read`（读 trialTask.inputs 里的输入文件） | `document` 节点。文本格式（txt、md、csv、json 等）用 `documentMode=local`；其他格式（PDF 等）用 `documentMode=agent`，工具 `native:read`，open 注明这一步会调用模型 | `source`；每个输入文件一个节点，同一文件连续重读只保留最后一次 |
| 写入之前对输入文件调用的解析或转换工具（参数里有该文件路径，目录里有对应的 `native:` 工具，read、glob、grep 等普通文件工具除外） | `document` 节点，`documentMode=tool`，`toolId` 为该工具；同一文件已按 agent 模式读过时改成 tool 模式 | 装文件路径的参数名作 `documentSourceKey`，其余参数原样放进 `inputs`；试做结果没有 `text` 字段时，取最长的字符串字段（不含文件路径本身）作 `documentTextPath` |

产物的写前探测和写后回读不另建节点：写入模块自带精确探测、回读和窗口核对（输出 check/checkNote）。写到产物以外的临时文件不进骨架。

读输入文件改用 document 节点（2026-10-26，§6.1）：它一次返回文件全文、不带行号，工作区路径和上传附件都能读；`native:read` 返回带行号的分页内容，作者还得另加代码节点拼回原文。PDF 这类 local 读不了的格式，优先用试做实际用过的解析工具（tool 模式，结果稳定），没有时才交给文档 Agent（会调用模型；读上传附件还需要能接收上传文件的工具）。LLM 节点不能读文件，不用于这一步。

其他工具（bash、web_fetch 等）没有固定节点。官方工具的前置条件和能否重复执行未知，Host 不把它们做成固定节点（T18，2026-10-27）。试做在写入产物之前用这类工具做了一步、输出写进了产物、方法也没把它列为排除时，骨架把这次调用起草成 Agent 节点（T28.3，2026-10-28）：子 Agent `runner` 在 roles 里声明并绑定，tools 填这个工具，prompt 是试做的原命令；命令里试做列过的匹配模式在草稿里换成 `input.pattern` 参数，核对节点不写死命令输出里的文字（文件名、哈希）；命令输出到最终正文的解析留给作者（render 占位）。写入之后提到产物路径的调用是复核，归写入模块和核对节点。其余用到的这类工具仍列在 open 里，提示需要这一步时用 Agent 节点。read、glob、grep、ls 这类查看不算一步。开头的 input 节点、结尾的 output 节点、数据整理（template/code）和核对逻辑都不进骨架，列在 `open` 里由模型补。

## 4、交给模型的形式

模板填写（template-fill）的生成提示里新增 `trialSkeleton`，与 `procedure`、`trialEvidence` 并列：

- `forms` / `modules`：可直接放进 create 提交的节点与模块声明，key 为短名（fetch、select、extract、save、read）。
- `order`：骨架节点的建议顺序；`sources`：每个 key 来自哪条试做证据。
- `open`：明确待补的部分：开头 input（start）与结尾 output（result）；写入前的整理节点（render，template 或 code）；产物检查等机械核对接在写入模块之后。
- `instruction`：以骨架为起点直接沿用其配置；需要改动或删除骨架节点时，在 assumptions 写“骨架调整：<key>：理由”。把网址或路径改成 `{{input.字段}}` 参数不算调整。

骨架用到的模板（http、HTML 处理工具、读取工具）随首轮提示一起预取，模型不必再查询模板。

不改编译器、提交格式和校验：骨架只是输入事实，模型提交的仍是普通 create 文档，经同一编译、结构检查、前置条件检查和首次运行。

## 5、偏离骨架的记录

不锁死，也不因偏离而退回修补（退回会多一轮模型调用，违背提速目的）。发布时 Host 对比骨架与候选：

- 骨架节点在候选里找到同类节点且关键配置一致（网址、选择器与字段、写入路径）→ 沿用。
- 找不到或关键配置不同 → 记为调整；assumptions 里有“骨架调整：<key>”的写明理由，没有的标“未说明理由”。

把值改成 `{{input.字段}}` 参数（包括嵌在 fields 等对象里的单个选择器）都算沿用。对比结果放进发布回执 `verification.trialSkeleton: {used, adjusted:[{key, reason}], meaning}`，主 Agent 汇报时如实转述。骨架由冻结的试做证据确定性生成，发布时重新计算即可，不另存。

## 6、完整草稿

2026-10-26 用户要求“把骨架补成更完整的草稿，试试能不能再缩短思考时间”。r36 A 用了骨架后作者阶段仍思考约 8.5 分钟，思考内容主要是模板写法、开头参数、状态码分支、回读核对和检查代码——都是骨架 `open` 里留给模型的部分。因此在骨架之外，Host 再按同一试做证据把这些部分补齐，生成一份完整的 create 提交 `trialSkeleton.draft`。

草稿的节点链：`start → fetch → fetchOk → select|extract → render → save → check → result`。

- start（input）：参数 `url`（多个网址时 `url2`…）和 `outputPath`，默认值取试做用过的值；fetch 的网址、等于该网址的 baseUrl 改成 `{{input.url}}`。
- fetchOk（code）：状态码不是 2xx 就报错，节点名写明“检查状态码”。
- render（template）：由试做写出的文件反推。用 select 结果里能完整解析的记录逐字对上写出的文件，前后不变的部分作为头尾，中间每条记录一行；编号列表（行首 `1.`、`1)`、`1、`）的序号用 `{{loop.index}}`；同一字段在一行里出现多次（如链接既作文字又作地址）时每处都换成引用；试做写入前把字段整理过（去首尾空白、`owner / repo` 写成 `owner/repo`、转小写）时，按模板过滤器能表达的同样整理去对（`trim`、`replace(" / ", "/")`、`lower` 及其组合，取最简单的一种），引用里带上该过滤器；试做的写入记录被截断时，只用截断前完整的记录核对，条数取 limit，列表之后的结尾段不猜，在 `open` 注明；用同一模板引擎 `renderDataTemplate` 重新渲染，已知记录必须逐字一致，其余记录按同格式计数，总数必须等于 limit（结果被截断时按 limit 补足）。反推失败或只有正文提取时，模板退回 `{{select.text}}` 一类占位，并在 `open` 标注 `verified=false`。
- 需求或过程说明要求“逐条/逐个用同一模板”时，整理拆成两个节点：迭代节点 lines（逐条执行）里放一行模板 line，render 只负责合并并补序号（`{% for row in lines.result %}{{loop.index}}. {{row}}`）。节点名与实际行为一致。
- save：`verified-file-write@1.1.0`，target `{{input.outputPath}}`，content `{{render.text}}`。
- check（code）：只检查 trialTask.artifacts 里的文本要求、写入模块回读结果 `save.check==='window-match'`，模板已反推时再检查条数。
- result（output）。
- coverage：过程步骤按 evidenceRefs 对应到节点（写入 → render、save；产物探测/回读 → save、check），对不上的步骤覆盖全部节点。

### 6.1、输入文件与原样写入（2026-10-26）

起因：“T05 附件另存为文件”（Desktop r44 安装，glm-5.3-flash Max）生成阶段用了 16 分钟。Host 给的草稿只有 6 个节点，但读取节点写死了试做用的工作区路径，需求却是运行时上传附件；`native:read` 又带行号。作者因此抛开草稿自己设计，第一次思考 8.5 分钟，把附件对象直接传给 `file_path`，被编译器拒绝；修补时再思考约 3.8 分钟，最后猜了一个不存在的 `{{input.attachment.path}}`，做出 15 个节点。

现在草稿按下面的规则处理输入文件：

- 开头参数：试做任务或过程参数里提到“上传 / 附件”，输入文件就是运行时上传的附件，start 加 `file` 字段（类型 file、必填，多个文件依次为 `file2`…），读取节点改名“读取上传附件”；否则加路径参数 `inputPath`（默认值是试做读取的路径）。两种情况读取节点的 `source` 都写 `input.字段`。
- 原样写入：试做写出的内容与读到的正文逐字一致（只容许末尾一个换行的差别）时，不加 render 节点，save 的 content 和 check 的 content 直接用 `{{read.text}}`，open 注明 verified=true。读到的正文由完整的 read 结果（逐行编号连续、带文件结束说明）还原，结果不完整就不判为原样写入。
- 其他情况仍按上文加 render，正文先占位。

用这次的真实试做记录重建，草稿为 `start → read（读取上传附件）→ save → check → result`，同一编译器直接通过。

节点目录同步补充：input 节点说明上传附件在运行时是 `{name, mimeType, size}` 对象，没有正文也没有 path；读附件正文用 document 节点，`source` 写 `input.字段`。编译器发现引用附件对象上不存在的字段（如 `input.attachment.path`），或把附件对象传给要求字符串的工具参数时，诊断里直接写明这两条。

不生成草稿的情形：骨架里有多个写入模块、过程步骤有 requiresReview、或没有可接到写入的数据节点。此时仍按 §4 给骨架。

Host 在交给模型前，用同一个编译器、同一 binding、同一 coverage 校验把草稿提交一遍；不通过就丢掉草稿，退回 §4 的骨架（`draft:false`）。所以交给模型的草稿一定能原样提交。

作者重抄草稿时漏掉工作流级 `title`：create 的名称本来就由请求定死（字段合同是 `const` 请求名称），Host 在工具参数校验前按请求名称补上，并把补好的参数交给原生工具提交；写了别的名称照旧退回修补。修改（edit）不补。

草稿交给模型时，提示里不再重复 forms/modules/order，只给 `draft`、`sources`、`open` 和说明：草稿可原样提交，提交时保持草稿结构（模块留在 modules，不加草稿没有的属性）；按需求改名、改参数、改模板都可以，改动或删除草稿节点在 assumptions 写“骨架调整：<key>：理由”。仍是普通 create 文档、同一编译与首次运行，不锁死、不降低思考强度。§5 的偏离记录照旧。
