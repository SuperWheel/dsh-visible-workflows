# 工作流编译工具实现与 R7 接入

> 2026-10-21 说明：工作流预算系统已于 2026-10-20 移除（见 [S12](tasks-规划提速与上下文复用.md)）。本文涉及预算问答、额度、增额或费用的内容仅为历史记录，不再执行；Token 用量只作性能计量保留。

实施基线：`be0394c`，即 R7 暂停交接后的代码。原始 R7 任务保持暂停；本次使用独立测试任务、临时运行目录和冻结的公开失败参数。实现与测试均不等于安装、发布或原业务任务验收完成。

## 1、实现范围

表 1-1 编译与执行边界

| 部分 | 当前行为 |
| --- | --- |
| 专用工具 | 包内 `workflow-compile` 命令；源码 `pnpm workflow:compile`；库导出 `dsh-visible-dynamic-workflows/compiler` |
| 输入 | Host 绑定的上下文 + `{submission: ...}`；新建用声明、修改用字段增量 |
| 编译 | 短名解析、稳定身份预留、连线展开、配置检查，再调用现有编辑编译与 Workflow 全量校验 |
| 局部修复 | 保存失败草稿和 revision，按允许区域应用原子补丁；成功后才交给原生终止工具 |
| 产物 | 现有 `Workflow`；交换格式仍为 `formatVersion: 2`、`runtime.engine: graphon` |
| 执行 | 专用编译工具不调用模型、不执行业务、不保存工作流、不发布提案；执行仍由现有 Graphon 链路负责 |
| 切换 | Host 配置 `planningCompiler: compact-repair`；可设为 `legacy`。旧持久化任务没有新模式标记，继续按旧语义读取 |

创作接口、修复状态机和来源提炼编译器均为可独立调用的模块。Host 在现有 `structured_output` 终止工具之前调用相同模块。没有增加一个要求模型“编译成功后再确认”的工具往返。

## 2、调用方式

### 2.1、独立进程

在项目根目录运行：

```sh
pnpm --config.verify-deps-before-run=false workflow:compile < docs/examples/workflow-compile.ndjson
```

构建后的包提供：

```sh
workflow-compile < input.ndjson
```

第一行必须来自可信调用方：

```json
{"context":{"workflow":"完整当前 Workflow 对象","operation":"create 或 revise","targetNodeIds":[],"nodeIds":["Host 预留身份"],"subagentIds":[],"environmentIds":[],"tools":[],"model":{"provider":"宿主供应商","model":"宿主模型"}}}
```

上例是字段说明；可执行输入见 `docs/examples/workflow-compile.ndjson`。绑定成功后返回工具 schema 和说明，后续每行提交一个 `submission`。进程只能绑定一次，接受候选后退出。失败返回非零退出码。调用方应把第一行和模型输入通道分开；编译成功不授予写入或执行权限。

示例连续产生 `bound → repairable → accepted`，并输出当前 JSON 包。新建声明写 `nodes:[{key,kind,config}]`、`chains:[{key,nodes}]`，分支另写 `links:[{key,source,target,port}]`。`start`、`result` 绑定新建基线的入口和默认出口。配置引用为 `{{format.text}}`；固定身份由 Host 分配。

修改声明使用 `mode: edit` 和 `updates:{n2:{set:{text:"..."}}}`，不重抄原图。显式删除用 `unset`；节点、角色、环境声明分别增删。容器子节点用 `scope`，不得提交 `config.body`。角色和 Secret 声明继续走现有验证，Secret 不得含值。

### 2.2、库接口

```ts
import { WorkflowAuthoringCompiler, exportWorkflowPackage }
  from 'dsh-visible-dynamic-workflows/compiler'

const compiler = new WorkflowAuthoringCompiler(hostContext)
const result = compiler.submit(modelArguments)
if (result.ok && result.value.candidate) {
  const jsonPackage = exportWorkflowPackage(result.value.candidate)
  // 按现有权限、版本和发布流程处理；编译器不会写入。
}
```

一个实例对应一个冻结任务。无效草稿通过 `snapshot()` 读取，已接受结果不可二次提交。进程重启后不自动重放草稿；Host 保留草稿用于诊断，将中断任务按原规则标记为 interrupted。

## 3、局部修复算法

1. 检查 JSON 大小、深度、危险键及普通对象要求，生成独立副本。
2. 首次声明把节点列表规范化为按 key 索引的修复视图，例如 `/nodesByKey/format/config/text`。重复 key 不会被静默覆盖。
3. 缺失的创作 `mode` 直接由冻结的 Host 操作补齐；显式冲突模式仍拒绝。配置字段先调用当前节点 schema 检查，随后展开为现有编辑操作并物化 Workflow。短名与预留身份在本次编译会话内不复用。
4. 汇总诊断，返回草稿 revision、相关片段、允许修复路径和剩余提交次数。未知字段允许修改同一个受影响对象，支持字段改名；缺失字段可以补齐。没有字段路径的对象级约束错误仍提供合法修复范围。
5. 补丁在副本上顺序应用，任一操作失败则整批回滚。支持 `add`、`replace`、`remove` 和唯一精确匹配的 `replace-text`，不做模糊文本替换。
6. 对修复后的完整结果重新编译和校验。补丁范围限制不替代固定节点、目标范围、引用、来源、Secret 和 Host 元数据检查。
7. 失败后的下一次模型请求只展示修复/必要澄清 schema，避免再次选择完整创作提交；底层原生工具保持原绑定契约。补丁可带有不改变业务数据的有界 `summary`。CLI 在失败回执中返回下一阶段 schema。
8. 有效结果等待原生 `tools/result` 成功回执后接受。最终权限拒绝、取消、回执不匹配或清理失败均不返回成功候选。

创作最多三次提交，提炼最多两次提交；优化合计仍保留两次提交额度。澄清沿用既有轮次上限，真实模型步骤和子任务继续受 R7 总预算控制。反复提交同一草稿和错误会提前停止。原始模型编辑协议仍最多 200 个操作，可信声明展开最多 2,000 个内部操作，避免 120 个节点的合法声明因展开后的冗余动作数而被拒绝；最终图的原有限制不变。

首轮预填最多五类相关节点语义。修改大图时保留全部节点索引、连线和输出字段，省略无关配置；确需了解其他节点时，通过只读 `planner_graph_context` 批量取回。该工具仅在修改任务中开放，返回本任务冻结快照。

## 4、R7 衔接

`execute-first` 的任务、真实试做、独立验收和人工复核入口保持原样。后续改为：

```text
原试做及验收回执
  → typed procedure 提交 / 同一 child 内补丁
  → 精简创作声明 / 同一 child 内补丁
  → 现有来源映射、readiness
  → 有限优化与 Graphon 样本回归
  → 预览或原发布流程
```

提炼阶段直接提交 `procedure` 对象，由 Host 生成既有内部 `procedureJson`。`evidenceRefs` 只接受冻结执行事件 ID；新增可选 `specRefs` 只接受冻结 `trialTask` 的实际规范路径。规范引用不能替代执行证据，每个步骤仍至少有一条事件证据；所有事件仍必须被步骤或排除项覆盖。`reviewItems` 和 `requiresReview` 的原有要求保留。

历史失败回归样本来自交接文件记录的那次公开 `structured_output`，包含原始参数摘要、冻结证据和规范。原失败有 11 处非法引用：10 处试做规范引用和 1 处 `requirement.R1`。一批补丁将规范明确迁入 `specRefs`，移除图外设计控制的伪证据排除项；五个业务步骤及复核条件保持不变。没有直接访问或复制模型的私有推理记录。

优化器先在本会话内修正配置、替换范围和来源声明，随后仍通过已有 Graphon 回放与候选选择。Graphon 运行失败的后续优化仍受原两轮上限约束；本次没有把所有规划阶段合并成一个无限循环。

已有旧规划任务不原地切换编译协议。之后若用户明确要求恢复交接中的已验收试做，应在原主对话中通过 `visible_workflow_plan` 发起新的规划请求，保留原 `trialId`、设置 `preview:true`，`source` 使用 `{kind:"verified-trial",trialId:"原试做ID"}`，不传 `execution`。现有 `planningEntry → resolveEvidence` 路径会核对原会话、工作区和验收摘要；新的规划任务采用当前编译器，原试做不重跑。查询新的规划 taskId，而不是修改旧记录的模式字段或复用已取消的规划 requestId。该恢复动作本次没有执行。

## 5、验证与证据

验证分三层：

- 编译与状态机测试：原子补丁、过期 revision、字段改名、缺失字段、多错误、固定节点、Secret、嵌套 scope、120 节点展开、唯一身份及 JSON v2 往返。
- Host 与 SDK 测试：已有 R7 试做来源、持久化与预览边界；实际已安装 SDK 的工具注册、作用域、原生终止、最终权限回执和清理优先级。该层模型由明确的离线替身替代。
- 真实模型对照：固定 GLM-5.3-Flash、high、temperature=0.2、8,192 输出上限；四组分别为旧接口、仅精简接口、仅局部修复、二者结合。生成的确定性图实际执行完整 Graphon 测试输入；另对 R7 记录的同一个失败对象比较整份重生成和局部修复。

结果、源码 SHA-256、请求数、首个流式事件耗时、供应商用量、公开提交参数和 Graphon 预期/实际输出存放在 `docs/evidence/workflow-compiler-20261018/`。凭据只在私有进程管道中用于已配置供应商认证，不进入证据目录；私有推理不落盘。字节数不冒充 Token；未知用量不按零处理。

开发试验先后发现未知字段改名范围、缺失已绑定 mode、根级诊断范围和修复阶段格式歧义，分别修复并保留各轮 `disposition.json`。失败的公开提交也做了独立离线重放；重放不计入真实提速。最终实验使用冻结版本重新运行，结果见该证据目录的 `REPORT.md`。

真实请求对照覆盖供应商、编译器和确定性 Graphon 校验，不包括 Desktop 界面、受控子 Agent 启动/销毁、Host 持久化与发布或原订单业务的完整重跑。小样本成功率不能证明原方案要求的 5 个百分点非劣界限，也不能替代原 R7 业务验收。未替换当前安装版，未恢复原暂停任务，未发布业务工作流。

已完成 48 次创作对照及两组共 8 次 R7 恢复对照，合计 118 次真实模型请求。组合方案相对旧接口的同任务配对耗时下降 66.7%，观察成功率均为 11/12；高上限 R7 恢复均为 2/2 成功，局部修复配对耗时下降 61.8%。完整失败记录与边界见 [测试报告](../../../../docs/evidence/workflow-compiler-20261018/REPORT.md)。全量自动回归 154 文件、1,810 项通过，另追加的原生 SDK 结构错误回归通过；类型检查、构建和独立 CLI 验证通过。


## r26 文件修改前置读取规则（2026-10-25）

- 用户依据 Desktop r26 工作流 `373a8569` 的已有文件裸写失败，决定“编译拦截+片段支持参数路径”；原因为冻结 SDK 的操作合同扩展缺失时，原 T18 合同校验跳过了 unknown 工具。冻结 `dsh-tool-fs` 的 write 和 edit 都使用 guarded mutation／`FS_NOT_OBSERVED`；本轮据其实际代码覆盖 `native:write`、`native:edit`，不猜测其他工具。
- 在共享 `planningCandidateIssues` 增加 planner 专用 `FILE_WRITE_NEEDS_READ`，包含节点 id 与路径，适用于 CREATE、EDIT 和 template-fill／compact-repair／legacy 物化路径。诊断可修复，建议使用 `verified-file-write@1.1.0` 的 input target，或添加同路径 read；修复允许节点、模块与连线范围，保留原提交上限和修复次数。
- 读取必须是到达写入节点前的依赖，覆盖全部激活分支；路径须为相同字面文本或相同完整的 input／节点输出引用，不推测别名、`./`、大小写或可变变量。仅在根 read 对容器入口必经且嵌套全为 loop 时继承观察；iteration 不继承 owner。缓存 read、仅并行读取、写后读取或仅一条条件分支读取均不能证明覆盖。文档工具模式会转换附件参数，必须改为显式文件工具节点。
- **首建兼容决策：** 无法静态证明“文件永远不存在”，所以裸新文件写入同样拒绝；但既有 T18 的精确探测→固定 exists 选择器→存在时 read／缺失时 create 图继续通过。这与 verified-file-write 的首建配方一致，避免无条件 read 缺失文件使运行失败。`native:edit` 没有首建例外。普通 glob、非空列表判断和任意自写选择器不能证明不存在；参数路径还须有固定路径校验守卫在 glob 前必经。
- 该规则仅用于 planner 候选；手动画布 `@Remote('save')` 仍按 parseWorkflow→storage.save 保存，不调用 planningCandidateIssues，不阻止用户手动保存裸写图。人工保存不等于运行时 SDK 允许覆盖；无隐藏预读、自动重试或权限改变。
- 原 T18 注册来源／摘要、参数和 T20 人审校验仍独立执行。旧 T24 参考导出保持原字节，它们是运行输出 oracle，不当作当前合法规划候选；没有为历史 fixture 放行裸写。
