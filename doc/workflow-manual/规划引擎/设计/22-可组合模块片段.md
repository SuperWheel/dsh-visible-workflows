# 可组合模块片段（T24 方案 B）

> 状态：2026-10-24 用户批准，§9 三项均采用建议：实例记录存于工作流（方案乙）、内部节点自动写入模块片段备注、允许片段放入 loop／iteration。来源：[文档 21](21-T24模块库扩充范围.md)，用户选定方案 B。本文只定义机制；首批模块等[调研 21a](21a-工作流常见用途调研.md)完成后再定。

## 1、要解决的问题

现在的模块只能独立成为整张图：主 Agent 交接 `mode:'module'`，Host 用 `compileBusinessModule` 展开整张图，规划模型不参与。真实需求大多是组合，例如“抓网页 → 解析 → 渲染 → **安全写入文件**”。其中写文件这段最该交给固定实现，现在却只能让模型从头设计。

目标是让规划模型在一次 CREATE 或 EDIT 里，把模块当作一个“节点”和普通节点放在一起，并照常连线。Host 在该位置展开模块的固定实现，模型不写模块内部。

## 2、规则

1. **模块内部只由 Host 生成。** 固定节点、内部连线和固定代码来自已冻结、已验证的配方，模型只能填参数。
2. **一入一出。** 片段只有一个入口节点和一个出口节点。内部的分支或循环必须在出口前汇合；出口不能是 `output` 节点。这样片段在链中就能和一个普通节点一样连线。
3. **端口是唯一接口。**
   - 片段声明输入端口（参数中引用上游的字段）和输出端口（下游可引用的字段）。
   - 下游写 `{{片段key.字段}}`，Host 把它解析到出口节点。
   - 引用未声明的端口会被拒绝，并给出可选端口。
4. **实例可以自证。**
   - 每个实例记录模块 ID、版本、参数和节点映射。
   - 使用实例前，Host 用记录的参数重新展开配方，与图中的实际节点比较定义（id、kind、config、连线；不比较坐标、标题和备注）。
   - 一致时才视为模块实例；不一致（例如用户手工改过内部节点）时，视为普通节点，即“脱离”。
   - 脱离不报错，也不会被自动改回。
5. **两种编译器用同一份合同。** compact 与 template-fill 的片段声明、字段说明和端口规则完全相同；片段使用同一个 RepairSession 和同一套提交额度。
6. **不放宽现有约束。** 片段展开后的整张图仍要通过现有的全部检查：编译、作用域、固定节点、审核先于写入、工具合同和 T18 前置条件。片段不享受任何豁免。

## 3、声明方式

### 3.1、CREATE

在节点声明之外新增 `modules` 数组。compact 的 `nodes` 和 template-fill 的 `forms` 不变。

```json
{
  "mode": "create",
  "forms": [ { "key": "fetch", "template": "http", "values": { } },
             { "key": "render", "template": "template", "values": { "text": "..." } } ],
  "modules": [ { "key": "save", "module": "verified-file-write@1.1.0",
                 "parameters": { "target": "reports/daily.md", "content": "{{render.text}}" } } ],
  "chains": [ { "key": "main", "nodes": ["start", "fetch", "render", "save", "result"] } ],
  ...
}
```

- `modules[].key` 与节点 key 共用一个命名空间，可以出现在 `chains[].nodes` 中，也可以作为 `links` 的端点。
- 片段不能是分支源，因为它只有一个出口。
- `chains[].container` 或兼容的 `scope` 照常决定片段所在的作用域；scopes=any 的片段可以放在 loop 或 iteration 内部；verified-file-write 仅允许根作用域。
- `parameters` 的合同来自模块目录：
  - 字面量参数（例如 `target`）按模块规则校验，例如必须是工作区根相对的字面量路径；
  - 端口参数（例如 `content`）只接受对上游的引用，或对容器 `item`／`index` 的引用。
- 数组中每种模块各有一个 `oneOf` 分支，`module` 字段用 `const` 固定，所以每个分支只展示该模块自己的参数合同。

### 3.2、EDIT

| 字段 | 作用 |
| --- | --- |
| `addModules` | 新增片段，形式同 CREATE；用 `addLinks` 接入已有节点 |
| `updateModules` | `{实例key: {parameters}}`，只改参数，由 Host 重新展开并比较 |
| `removeModules` | 删除整个实例的全部内部节点；接入的连线照常需要处理 |

编辑上下文中，一个有效实例只显示为一行：`{ref, module, parameters, ports}`，不展开内部节点。这样上下文更短，模型也看不到、改不了内部节点。

已脱离的实例按普通节点显示。

### 3.3、模块目录

在现有 `businessModuleCatalog` 条目上新增：

```ts
fragment?: {
  inputs: Record<string, {type, description}>,   // 端口参数
  outputs: Record<string, {type, description}>,  // 下游可引用字段
  scopes: 'any' | 'root',                        // 是否允许放进容器
}
```

- 命令简报和 template-fill 的模板目录查询都会列出带 `fragment` 的模块，内容包括适用条件、端口和参数示例。
- 目录里每个片段只写一句用途说明。

## 4、Host 展开

在 normalize 之后、`AuthoringCore.compile` 之前执行，作为纯函数 `expandModuleFragments(document, catalog)`：

1. **校验参数。** 按模块合同逐个检查；字面量参数在这里就要合法。
2. **复制内部节点。**
   - 按配方复制内部节点，key 为 `片段key__角色名`，例如 `save__probe`、`save__write`，不与其他节点冲突；
   - 配方中的内部链按片段所在作用域生成；
   - 嵌套容器沿用现有 `chains[].container` 的写法。
3. **接线。** 外部链里的 `片段key` 换成 `入口 … 出口`；把 `links` 中以片段为端点的连线改到入口或出口。
4. **解析端口。**
   - 把参数中的端口引用写进内部节点配置；
   - 把其他节点中的 `{{片段key.字段}}` 改写为 `{{片段key__出口.字段}}`；
   - 字段必须是已声明的输出端口。
5. **记录实例。** 为每个片段生成 `{instanceKey, moduleId, version, implementationDigest, parametersDigest, roles:{角色名→key}}`。编译后，Host 用分配的节点身份把 key 换成节点 ID。

展开失败（例如参数非法或端口未声明）时，按普通编译问题返回：

- 反馈路径指向 `/modules/<key>/parameters/...`；
- 片段内部节点的路径不会出现在 `allowedPaths` 中。

## 5、实例记录存在哪里

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 甲：存于规划任务（沿用 `task.moduleProvenance`，改为数组） | 编辑时向前查找已发布任务 | 不改工作流存储格式 | 实例记录分散在任务链中；用户手工修改图或导入导出后难以追溯；多次规划后查找链变长 |
| **乙（建议）：存于工作流** | `Workflow.moduleInstances?: [...]`，随图保存、导出、复制 | 记录与图在一起，最直观；依靠规则 4 的比较自证，不需要信任记录来源 | 与 T26 的 `note` 一样，旧版严格 schema 会拒收，需要复用回退脚本，去掉该字段 |

建议选乙。安全性不依赖记录在哪里：即使记录被篡改，比较定义时也会对不上，实例按“脱离”处理，按普通节点对待；Host 不会因为有记录就放行。

## 6、与现有机制的关系

- **整图模块保留。** 主 Agent 的 `mode:'module'` 交接、`compileBusinessModule` 和 `revise-parameters` 不变；两个现有模块的冻结摘要也不变。
- **固定节点保护。** 实例内部节点并不标为 `fixed`（`fixed` 是用户的意图）；模型只是改不到它们，因为 EDIT 合同里没有这些节点的字段。用户在画布上仍可手工修改，改后实例按“脱离”处理。
- **画布。** 第一版不加分组框；内部节点照常显示，由 T27 自动整理。可以在节点备注中写入“模块片段：模块名 · 实例 key”作为提示。这一点待定，见 §9。
- **Host 确定性修复（T26）。** 片段只能有一种写法，唯一修复规则不需要额外分支。

## 7、验收

- **离线：**
  - 展开纯函数的正例和反例：参数非法、端口未声明、作为分支源、多入口；
  - 片段放在容器中，以及同一张图里有多个片段；
  - 脱离判定；
  - 两种编译器的合同字节一致；
  - 两个现有模块的冻结摘要不变；
  - 每个新模块各有一份冻结摘要和运行夹具，在隔离存储中实际运行，包括写入和回读。
- **回放：** 用文档 21 §2.2 的真实需求（如库存补货清单、R7 订单汇总），手工写出带片段的提交，展开后与正确的手写图比较语义。
- **Desktop：** 新建一个带片段的工作流；在隔离工作区运行一次；再改一次片段参数。真实模型复测需另行批准。

### 10.2、实例自证、编辑与存储

- `Workflow.moduleInstances` 通过严格 schema 保存，记录参数、摘要、角色→节点 ID，作用域，以及创建时的相关边快照（仅作参考，见 §10.3 第 4 条）。参数引用先转换为实际节点 ID，避免依赖上一轮临时 key。
- 每次消费记录均重新解析参数、展开当前冻结配方，再比较实际 id／kind／config、内部连线及作用域，并检查外部连线只接入入口、只从出口离开。容器配置按递归执行定义比较；坐标、标题、编号、备注和边的随机身份不参与比较。参数摘要、实现摘要、版本、角色、作用域或内部连线不符，或外部连线越过入口／出口边界，即脱离；重复 key／重叠角色记录也不作为有效实例。
- 脱离只影响呈现与片段编辑入口：内部节点按普通节点出现，可在原授权范围内编辑；不抛出脱离错误，不改回配方，不自动删除历史记录。
- 有效实例在编辑视图中折叠成 `{ref,module,parameters,ports}`；内部节点不出现在可编辑 updates 或图查询里，外部边与配置引用改用公共实例 ref。更新只重新生成参数对应的配置，节点 ID、坐标和已有备注保留；删除整个实例仍需满足原删除目标授权及整图检查。
- Host 为没有备注的内部节点写入“模块片段：模块名 · 实例 key”；不覆盖已有备注，修改备注不导致脱离。
- 工作流投影、存储、导入、导出及实际主页卡片复制均保留记录。导入／复制同步重映射 roles、scope、边和参数引用；原本不匹配的参数摘要不会被顺手修成有效摘要。浏览器导入使用与 Host SHA-256 等价的同步 JSON 摘要实现，未给客户端引入 Node 内置模块。

### 10.3、合同投影与修复路径的具体取舍

1. 已安装 SDK 要求 `oneOf` 至少两个分支。目前只有一个片段，故沿用仓库 `planningOneOf`：单分支直接投影为该对象，`module` 仍为 `const`；未来多个片段自然使用每模块一分支的 `oneOf`。两种编译器的片段合同字节一致，初始／下一轮合同均经过 SDK 结构校验。此项属于 SDK 所需的等价投影，没有加入备用业务模块凑分支。
2. 普通公开 key 仍支持完整的 1–40 字符。展开纯函数保留 `key__role` 命名；超过旧编译器 key 长度的 Host 生成名称只在编译边界使用私有短别名，保存时角色均换成实际 ID，不增加 key 或身份预留上限。若保存的实例 key 与下一次 EDIT 的 `nN` 引用重名，编辑上下文分配无冲突 ref；记录的实例 key 保持不变。
3. 参数错误指向 `/modules/<key>/parameters/...`（EDIT 使用对应的 add／update 根）。未声明输出端口同时列出有效端口；下游引用写错时，还开放该引用原来的公开字段路径，否则仅修改模块参数无法修正拼错的输出字段。内部节点路径不进入 allowedPaths。历史 r12 的结构性修复根相应增加公开 `/modules`，原反馈证据未改写。
4. 实例记录额外保存 scope 和创建时的相关边快照。scope 参与比较：片段被移到其他容器即视为脱离。
   - **2026-10-24 复核修正：** 外部连线不再与快照逐条比较。原先的做法会让“后续编辑或手工新增片段输出的下游消费者”立即判为脱离。现在改为检查边界：外部连线只能接入入口、只能从出口离开，内部连线必须与配方一致。快照 `edges` 只保留为创建时的参考，不参与判定。
   - 回归测试 `keeps an existing instance valid when a later edit adds a consumer of its output port`，以及分支、容器两种配方的入口外泄反例，在旧判定下失败，修正后通过。

### 10.4、回退步骤（沿用文档 19 §10.5）

旧版严格 workflowSchema 不认识 `moduleInstances`，nodeSchema 也不认识 `note`。回退前先停止使用该存储的插件，再从当前源码运行：

```sh
node scripts/strip-node-notes.mjs /明确指定的存储根目录
node scripts/strip-node-notes.mjs /明确指定的存储根目录 --apply
```

第一条默认 dry-run，列出带备注的节点及带模块实例记录的工作流，不写文件。第二条先将 `library.json` 原字节备份为同目录 `library.json.before-strip-node-notes-时间戳-进程号.bak`，再递归删除节点备注，并删除工作流顶层的整个 `moduleInstances` 字段；只有实例记录、没有备注时也会备份并处理。原有并发变更检查与原子替换保留。脚本只访问显式存储根，不发现默认目录，不读取 Desktop profile。恢复可在停止插件后使用该备份还原完整 `library.json`。测试全部使用临时目录。
