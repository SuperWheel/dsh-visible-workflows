### 2.2、Desktop 库里的真实业务图

除去测试夹具（T05／T06／S10 合成图、T20／T23 复测图），真实需求都是同一种形状：**取数据 → 处理 → 渲染 → 写文件**。

| 图 | 取数据 | 处理 | 渲染 | 写文件 |
| --- | --- | --- | --- | --- |
| GitHub Trending 每日 Top 10 报告 | `native:web_fetch` | llm 提取＋code | code 生成 Markdown | `native:write` |
| GitHub Trending Top10 日报 | `http` | code 解析 | template | `native:write` |
| R7 订单汇总 | `native:read` | code 解析／汇总 | template | `native:write`×2，再回读，然后 human 核对 |
| 库存补货清单 | 输入 | code 计算 | template | `native:write` |

所有真实业务图都要写文件，而且写之前都没有精确探测或读取目标。按 T18 的规则，覆盖已有文件前必须先精确读取目标，首次创建前必须先证明目标不存在。模型很难每次都写对这一步，`reviewed-file-write` 已经把它做成固定实现。

## 3、关键选择：模块是否可以组合

| | A：继续做独立整图模块 | B：可组合模块片段 |
| --- | --- | --- |
| 做法 | 每个模块覆盖一整类需求，例如“网页提取”“列表逐项处理” | 模型在 CREATE 中声明 `{module, parameters}` 片段，与普通节点一起连线；Host 在该位置展开固定实现，片段之间用固定的输入／输出端口相连 |
| 命中真实需求 | 低：2.2 节的图都是组合，整图模块对不上 | 高：写文件片段可接在每张业务图末尾，列表处理片段可放进任意图 |
| 改动量 | 小：照现有两个模块的方式加 | 中到大：两种编译器的合同、作用域内展开、端口契约、revise 的实例来源映射，都要改 |
| 风险 | 低 | 片段内部节点仍是固定实现；风险在连线与作用域，需要新的回放和 Desktop 验收 |

**建议选 B**，并按 4.1 节从“安全写入文件”片段开始：它在真实需求中出现最多，正确性最难靠模型保证，而且可以直接复用 `reviewed-file-write` 中已验证的探测／读取配方。

## 4、候选模块（按建议顺序）

### 4.1、`verified-file-write`：安全写入文件并回读核对（需要方案 B）

- **固定实现：**
  - 精确探测目标：`native:glob` 加固定的存在判断代码。
  - 已存在时先 `native:read`，再按当前版本写入；不存在时首次创建。
  - 写入后 `native:read` 回读，并与写入内容比对。
  - 输出 `path`、`written` 和回读结果。
- **参数：**
  - `target`：字面量工作区根相对路径，与 `reviewed-file-write` 的规则相同；
  - `content`：上游引用；
  - 是否需要回读：默认需要。
- **依据：** 2.2 节中 4 张真实图都写文件；T18 的写入前置条件；`reviewed-file-write` 的探测与读取部分已经离线和 Desktop 验证。
- **不含：** 人审。需要人审的需求继续用 `reviewed-file-write`。

### 4.2、`list-map`：列表逐项处理并收集（独立整图可先做；组合后价值更大）

- **固定实现：**
  - 由 iteration 容器遍历输入数组；
  - 每项执行一个 template，正文作为参数；
  - 按顺序收集每项的 text，输出紧凑 JSON 数组，空数组输出 `[]`。
- **依据：** 基准中最贵的结构（中位 99 s，失败 17/74，需修复 29/74）。成绩分级这类需求也属于“逐项判断再汇总”。
- **注意：** 模块只固定容器、入口和收集这套结构；每项的业务逻辑只允许是 template 文本，代码逻辑不进模块。

### 4.3、`web-extract`：网页抓取与正文提取（独立整图可先做）

- **固定实现：**
  - `http` GET，URL 模板作为参数；
  - 用固定 JS 提取 title 和 main 的纯文本：去标签、合并空白，main 为空时用“空”；
  - 输出 `title` 和 `text`。
- **依据：** 基准第二贵（中位 89 s，需修复 18/72）；两张 GitHub Trending 图都要抓网页。
- **注意：** 不同站点的结构不同，模块只做通用的 title／正文提取，不负责“解析 Top 10”这类站点专属逻辑。

### 不建议做成模块

- **structured-llm：** prompt 和输出 schema 因需求而异，固定实现能复用的部分很少。
- **branch、tool-wrapper、greeting：** 已经很快（中位 21–38 s），收益小。

## 6、方案 B 的设计要点（选定后展开成实施文档）

- **声明方式：** CREATE 与 EDIT 的节点声明中，增加一种 `module` 形式：`{key, module:"id@version", parameters, scope?}`。两种编译器使用同一份合同和同一份字段说明。
- **展开：** Host 在片段所在的作用域内复制固定节点，分配新的节点身份，再把片段的入口端口接到上游、出口端口接到下游。片段内部的连线不由模型写。
- **端口契约：** 每个片段声明输入字段（例如 `content`）和输出字段（例如 `path`、`written`）。下游引用片段输出时，按 `{{片段key.字段}}` 解析到片段内对应的出口节点。
- **修改：** 片段实例记录来源映射。修改参数时沿用现有 `revise-parameters` 的规则；片段内部节点视同固定节点，模型不能直接修改。
- **验收：**
  - 用 2.2 节的真实需求，例如库存补货清单，回放 CREATE；
  - 对比片段展开后的图与手写正确图的语义；
  - 冻结摘要不变；
  - 跑一次 Desktop 新建并实际运行一次，在隔离工作区验证写入与回读。

## 7、综合建议：本地需求 × 大众用途（2026-10-24 用户确认首批四个）

[调研 21a](21a-工作流常见用途调研.md) 用 40 个公开来源补充了第 2 节的本地证据。我抽查了两处关键数据，均与原页面一致：Zapier Q2 2026 中，1,500 家客户里采用 AI 工作流最多的 375 家，AI 角色占比为 Communicator 53%、Clerk 45%，AI 步骤占 18%；n8n 模板库共 13,649 个。

调研对本文的修正：

- 大众用途主要不是“写本地文件”，而是抽取后写入记录、发消息、知识问答，以及 AI 与确定性步骤混合的流程。这支持方案 B。
- 第 4 节“structured-llm 不建议做成模块”需要修正：prompt 确实因需求而异，但“抽取 → 校验 → 失败分流”这层外壳是固定的，值得做成模块。
- `list-map` 只允许逐项用 template，范围偏窄，应改名为 `list-map-template`，抽取等变体以后另行冻结。

综合排序。依据有四：大众覆盖、本地需求、能否冻结验证，以及当前工具是否具备（不确定的连接器往后排）。

| 批次 | 模块 | 主要理由 | 首版边界 |
| --- | --- | --- | --- |
| T24.2 首批 | `list-map-template` | 大众跨平台出现；本地基准中最贵、最易错（中位 99 s，失败 17/74） | 逐项只用 template；保证空数组和顺序 |
| T24.2 首批 | `extract-validate` | 大众第一，Clerk 角色有运行数据 | 复用已有 extractor／llm 输出；固定类型与必填检查，输出 `ok/data/errors/source`；不承诺语义正确 |
| T24.2 首批 | `web-extract` | 大众与本地都有，第二贵 | 静态 HTML；输出抓取状态，空正文有明确状态，不执行脚本 |
| T24.2 首批 | `verified-file-write` | 本地 4/4 业务图都写文件；复用已验证的配方，成本低 | 精确探测、读取、写入、回读；不含人审 |
| 第二批 | `retrieval-answer` | 大众客服和知识问答 | 首版明确为本地关键词检索 |
| 第二批 | `review-gate` | 由 `reviewed-file-write` 的门控推广而来 | 在图内展开；有界退回 |
| 以后（需先接入真实连接器） | 一个渠道的受审发送、一个系统的记录写回 | 大众热门，但本插件目前没有确定可用的 Slack／表格／CRM 连接 | 先选一个真实已连接的工具 |
