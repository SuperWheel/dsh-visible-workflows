# 审核写入模块与配方唯一写法（T22）

## 1、问题

2026-10-22 在 Desktop 用 `/dsh-visible-workflows` 新建 T20 审核写入图，子 Agent 思考很长，low 强度下修复三轮仍失败。

- **已有的提速方案没有丢。** [S01—S12](tasks-规划提速与上下文复用.md) 的直接编辑、局部结构编辑、模块实例化、切片预取、后台受理都在 r7 里生效；确定修改常常 0 次模型调用、几秒完成。
- **慢在新建复杂图。** 新建仍要子 Agent 设计整张图。T20 需要的“先审核再写文件”结构约 20 个节点，带 loop、human 和两次写入。
- **这段结构其实已有现成实现。** `reviewedFileWriteGraph`（`src/shared/planning-review-recipe.ts`）已有测试，但只作为 human 节点词典里的例子下发，模型要照着手抄一遍。
- **例子教的是被禁止的写法。** 例子是运行时格式：loop 的内部节点放在 `config.body`。新建协议恰恰要求内部节点独立声明、用 `{container, nodes}` chain 排序、不写 scope。失败诊断正是 `CONTAINER_ENTRY` 和 8 条 `NODE_SCOPE_MISMATCH`。

## 2、原理

- **已验证的结构由 Host 复制，模型只填参数。** 这是 S06 的原则（借鉴 Voyager 技能库、Sketch 固定骨架）：复制固定实现不需要思考，参数齐全时新增规划调用为 0。T20 这段结构正是研究文档 10 第 4.2 节列出的首批候选，当时没有做。
- **例子就是教学。** 词典里的例子和规则说法不一致，就等于教了两种写法，而且其中一种是禁止的（T21 的“唯一写法”原理）。例子要么改成协议写法，要么改成引用模块。
- **模块不限制设计自由。** agent 仍自己设计整张图；模块只替换其中已验证的一段。业务超出参数能力时照常局部设计。
- **不降低思考强度。** 用户明确要求保持思考强度；本任务只减少要做的选择和要手抄的内容，不改模型和强度。

## 3、改法

- **T22.1 审核写入模块。** 把 `reviewedFileWriteGraph` 登记为版本化业务模块 `reviewed-file-write@1.0.0`。参数：目标路径（字面量）、生成正文的方式（固定文本模板或引用上游）、最多轮数。Host 展开为现有 Workflow 节点图，固定实现、来源摘要与 S06 一致；参数更新只改受控差异。模块注册表从单一模块改为可扩展的多模块。
- **T22.2 词典例子改成唯一写法。** human 语义中的 `reviewBeforeEffect` 不再下发运行时整图，改为：优先使用 `reviewed-file-write` 模块；需要手写时给出新建协议写法（独立节点＋container chain，不写 scope、不写 `config.body`）。
- **T22.3 路由。** 主 Agent 识别到“审核后写文件”且参数齐全时，经 handoff module 路由直接实例化；需要在模块外再加业务节点时，子 Agent 只补其余部分。

## 4、验证

- 离线：模块实例化的图通过完整校验和 REVIEW_BEFORE_EFFECT 检查；与配方函数结果一致；参数更新只改受控差异；词典例子不再含 `config.body`。
- Desktop：重新跑 T20 建图，记录模型调用数、耗时；随后完成 T20 的拒绝与批准验收。
- 不另跑配对基准：词典与模块对两组同时生效，配对比看不出差别（T21 原理），以 Desktop 的绝对耗时和调用数判断。

## 5、实施结果

- 模块请求改为按 `moduleId` 区分参数合同；新增 `reviewed-file-write@1.0.0`。Host 调用原 `reviewedFileWriteGraph` 并转换为 CREATE 声明，再经共享编译展开 22 个节点，记录含内部节点的实例来源、参数摘要及固定实现摘要。
- 参数为字面量根相对 `target`、`producer:{text}` 模板、`maxIterations`（1–100，默认 3）。模板可引用 `reviewBase`／`reviewNote`；本版本固定使用原生 glob/read/write，不开放任意代码、模型或工具覆盖。参数更新保持身份与连线，只更新参数对应配置，校验现有实现、嵌套连接、来源与存储记录。
- 表格模块原参数合同、固定实现摘要及来源格式保持兼容；回归覆盖旧 v1 来源继续更新，并与 `8416d8a` 原实现比较实例来源及候选内容（忽略候选时间戳），结果一致。
- human 词典改为优先引用模块，手写例子采用独立节点及 container chain。loop／iteration 示例、词典中的创建 schema 和主 Agent 指引同步收口；运行时导入 schema 与编译器接受范围不变。已 grep 检查规划提示与词典，不再教授 CREATE 内嵌运行图。
- 离线覆盖参数边界、配方等价性、完整候选／审核／工具前置条件校验、参数受控差异、存储记录防篡改、模块创建及更新零 planner／driver 调用、模块外业务继续走子 Agent，以及 Host 离线启动。未改模型或思考强度，未调用真实模型。
- 验证结果：`npm run typecheck` 通过；相关 8 个测试文件共 230 项通过（修正夹具断言后单独复验 Host）；唯一一次全量 `npm test` 在沙箱外执行，249 个文件、3290 项全部通过。沙箱回环端口预检为 `EPERM`，因此未在沙箱内重复全量测试。
- T22.4（2026-10-23，r8）：Desktop 建图发送到保存 4 分 28 秒（r7 约 13 分钟），规划子 Agent 0、受理到保存 0.3 s；随后完成 T20 拒绝→通过验收。见 [证据](../../../../docs/evidence/t22-t20-desktop-20261023/README.md)。

## 6、新学到的原理

- **复制比思考快得多。** 同一张图，手抄配方要 18k Token 的思考，按参数实例化是 0 次模型调用；对已验证的结构，最好的提速是不让模型重新推导。
- **瓶颈会转移。** 子 Agent 消失后，剩余 4.5 分钟全在主 Agent 理解需求和查工具；下一步优化的对象随之变成主 Agent 轮次。
- **新检查必须兼容历史数据。** r6 因为新契约否决历史记录而整体无法启动；新规则只约束新候选，历史按证据读取，发版前用真实数据副本离线启动一次。
