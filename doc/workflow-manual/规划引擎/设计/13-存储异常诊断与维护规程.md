# 存储异常诊断与维护规程

日期：2026-10-21。对应 [Tasks T15](tasks.md)；异常来源与历史修复状态见 [06-后端全量审计与清理建议](06-后端全量审计与清理建议.md)、[07-后端阻断修复与桌面验收](07-后端阻断修复与桌面验收.md)、[12-后端五路审计与修复验收](12-后端五路审计与修复验收.md)。

本篇新增独立的只读清单与人工维护步骤。没有变更 Host 启动、运行淘汰、锁接管、提案接受或规划恢复的行为；也不以诊断替代数据备份、业务核对与恢复授权。

## 1、入口与证据边界

### 1.1、执行方式

在源码工作区安装项目依赖后执行，必须显式提供存储根目录；入口不会发现或读取默认 Desktop profile。以下路径仅为合成夹具示例，报告写在待检查目录之外：

```sh
npm run --silent storage:diagnose -- /private/tmp/t15-synthetic-store > /private/tmp/t15-diagnosis.json
```

`node --import tsx scripts/storage-diagnose.ts /private/tmp/t15-synthetic-store` 与其等价。去掉 npm 的 `--silent` 会有 npm 自身的命令横幅；脚本标准输出本身只有 JSON，参数错误写标准错误。

表 1-1 输出与退出状态

| 字段／状态 | 含义 |
| --- | --- |
| `readOnly: true` | 只读描述符、有界读取；不构造 WorkflowStorage / PlanningStore / EditorState，不获取 Host 锁 |
| `records` | 已观察路径的清单；含正常记录、目录和异常记录，异常存于各记录的 `findings` |
| `identity`、`references` | 文件设备／inode、运行／附件／提案／代次身份与引用关系；token 只输出 SHA-256，不输出原值 |
| `size`、`modifiedAt` | lstat 的字节数和修改时间；目录大小不是其内容总大小；无法取得时为 null，不能当作零 |
| `findings[].code/reason/suggestedAction/details` | 分类、理由、建议与可复核偏移／序号等，不导出附件原文或隔离原字节 |
| `complete: false` | 有链接、权限拒绝、超限或不能安全读取的路径；未检查不等于正常 |
| `consistency/observation: possibly-writing` | PID 存活，或读取前后身份／大小／时间变化；可能在写入，需停止写入后重查 |
| 退出 0 | 完成可读取范围的诊断；仍可能存在异常或 `possibly-writing`，必须查看 JSON |
| 退出 1／2 | 1 为范围未完整检查；2 为参数错误，不默认退回用户数据目录 |

### 1.2、只读的实际范围

只枚举显式目录及 `runs/`、`attachments/<runId>/`、`planning/`、`trials/planning/`；不按记录内路径打开工作区文件，不访问模型或外部业务服务。附件只读取当前存储的 JSON，以所属 runId 和 workflowFileId 核对引用。运行输入中的文件引用既包括对象，也包括运行器保存的 JSON 字符串。当前运行存在但附件未被快照字段直接引用时单列 `unreferenced-attachment`，不等同于没有所属运行。

不跟随根目录、祖先、受检目录或文件的符号链接；文件通过 `O_RDONLY | O_NOFOLLOW | O_NONBLOCK` 打开，并核对句柄与路径身份。普通 JSON 的诊断读取上限为 32,000,000 字节，日志为 128,000,000 字节；超限记录大小与未检查原因，不无限追读增长文件。检查覆盖存储外壳、运行图与基本执行结构；没有调用会写入的规划服务构造或其完整业务恢复流程，不能由清单推导任务发布授权、模型回执或业务结果正确。

Host 运行时可以执行：工具不争锁、不等待 Host 停止。文件变化、短读、消失或原子替换均保留观察并标为“可能在写入”。活 PID 只能证明进程存在，不能证明 Host 已初始化成功，也不能排除 PID 被复用；权限拒绝返回 unknown，不能当作进程已退出。没有可信的进程内 token 来源时，只比较同时存在的 `host.lock` 与 `host.lock.recovery`，不声称验证了进程内所有权。

两次元数据核对不是跨文件事务或敌对文件系统竞争的完整隔离证明。Host 活动时的孤儿、代次与提案差异均为待复查线索；即使没有活锁，也可能有启动、退出或其他维护进程。人工处置必须先让所有写入者退出并取得稳定备份。读取可能改变文件系统 atime；不改文件内容、目录成员、链接、权限、mtime 或 ctime。

## 2、异常含义与人工处置条件

表 2-1 分类与维护边界

| 清单分类 | 含义 | 人工处置的前置条件与方法 |
| --- | --- | --- |
| `orphan-attachment`／空孤儿目录 | `attachments/<runId>` 没有对应运行快照；可能是旧淘汰逻辑遗留，也可能正处于上传与快照落盘间隙 | 停写后复查快照、事件和备份，核对 runId；备份后可将确认无主的精确目录人工移至外部隔离备份，不按体积扫删 |
| `unreferenced-attachment` | 所属运行仍存在，但未发现该 workflowFileId | 保留所属运行关系，核对冻结输入、执行数据与历史用途；不能因字段未引用就当无主附件删除 |
| `attachment-reference-unknown` | 运行目录不完整或被链接重定向 | 先解决读取证据缺口；不能判定为孤儿 |
| `dead-lock-owner` | 锁中正 PID 返回 ESRCH | 同时核对 Host、恢复进程、PID 复用与两份锁的身份；确认无写入者、备份后，才可人工移走精确遗留锁 |
| `recovery-gate-present`／`lock-token-mismatch` | 恢复门锁存在，或两锁 token 不同；竞争接管也有短暂窗口 | 不自动强删。等待正在取锁者完成；停止后连续两次核对 inode、mtime、PID 与 tokenDigest 稳定，再调查遗留原因 |
| 活 PID／`unknown-lock-owner` | PID 存活或无权探测；F27 初始化失败也可能留下活 PID 锁 | 不凭“界面没出现”删锁；核对初始化错误、让所属 Host 正常退出。T15 不修复 F27 生命周期 |
| `symbolic-link`／`invalid-lock`／读取异常 | 链接、非普通对象、损坏锁 JSON 或缺少身份 | 不跟随目标；分别保存链接条目与本地路径元数据。核对预期布局与所有者后处理，不能把锁内容无效解释为无人持有 |
| `invalid-json`／`invalid-run-snapshot` | 运行快照截断、身份与文件不符、图或执行基本结构无效 | 先保存原字节；从已核对的同 runId 备份恢复，或人工隔离该完整运行证据集合。不能用空快照、改 ID 或放宽校验隐藏损坏 |
| `truncated-tail`／`invalid-jsonl-row` | 无法解析的未终止末行，或已终止坏行 | 末行可能正在追加；停写后保留偏移与原字节。中间坏行不能跳过或拼接，需专门恢复合同；T15 不执行截断 |
| `quarantined-event-tail`／隔离记录异常 | F25 已保存截断尾部的 runId、byteOffset、detectedAt、bytesBase64，或隔离记录自身无效 | 保留隔离文件与对应快照、事件日志一同备份；核对保存字节数和原偏移。存在隔离文件不表示当前主日志仍损坏，也不是可无条件删除的缓存 |
| `event-identity-mismatch`／`invalid-event-sequence` | runId、事件 ID 或序号重复、倒退、无效 | 按运行身份核对事件来源；不重排或重新编号以伪造连续历史。旧格式无 seq 行保留兼容，不因无末尾换行误报完整 JSON 行 |
| `planning-generation-mismatch` | tasks／background／trials 的日志头与快照 journal 不一致；旧代次会被当前读取器忽略 | 可能是快照替换后、旧日志清除前的压缩窗口。停写后对照两份原件，不把旧日志改成新代次或直接拼接；确认快照已完整涵盖旧任务后才可人工隔离旧日志 |
| 规划快照／日志头／任务行损坏，`journal-without-snapshot` | 格式不符合 PlanningStore 外壳，或日志没有快照而不会被重放 | 成对备份、按代次调查；不得拿孤立日志直接覆盖新快照。没有日志通常是延迟创建，不能单凭缺失日志报损坏 |
| `pending-candidate-already-saved` | pending 与 library 定义相同，可能是 F26 分文件提交中断，也可能是无改动提案 | 核对 proposalId、workflowId、baseRevision、library revision 和候选内容；通过正常接受入口重试补记状态，不手改 revision，不重复发布业务工作流 |
| `accepted-proposal-mismatch`／提案目标缺失 | accepted 候选与同版本定义不同，或库版本落后／目标不存在 | 备份 editor-state 与 library 成对核对。更高版本正常编辑不报此差异；不要直接把 accepted 改回 pending 或用旧候选覆盖新定义 |

## 3、维护步骤

### 3.1、备份与留证

1. 先保存诊断 JSON 到受检目录之外。记录源码版本、执行命令、退出码、存储路径、Host 是否活动及观察时间；敏感附件和工作流内容不复制到公共工单。
2. 安排维护窗口，让 Host 与恢复、导入或其他维护写入者正常退出。两次只读清单中的 PID、路径 inode、大小与 mtime 应稳定；单次退出探测不能代替确认。
3. 对整个存储根目录制作独立备份，保留 `library.json`、`editor-state.json`、运行快照、事件与 F25 隔离记录、附件、主规划／background／trials 快照和日志、两种锁及临时文件。复制链接条目本身，不跟随链接读出目录外目标；不要在原目录创建备份。
4. 给备份建立路径、类型、大小、mtime、权限与普通文件 SHA-256 清单，检查源与副本的成员和字节相同。无法读取的路径记录 unknown，先补齐备份证据，不以空文件替代。

### 3.2、精确处置

先依据表 2-1 确认处置资格，再逐项记录原路径、runId／proposalId／代次／锁身份、引用与阻断证据、备份位置、理由、操作者及时间。每次只处理已核实的精确对象；优先人工移至存储根以外、可回滚的隔离备份，保留原相对路径和清单。不在正常启动中增设扫删，不把历史附件清理扩展到已有运行。

损坏快照与日志没有通用“删除即可恢复”的规则。移走运行快照可能使该运行及附件不可访问；移走规划记录可能丢失提交或试做回执。没有同身份的可信备份或恢复合同，就保留原件并报告阻断。F26 优先使用已有的可恢复重试；不手工伪造提案接受或发布回执。

### 3.3、处置后验证与回滚

1. 先离线重跑只读诊断，核对目标异常变化、其余清单身份与文件 SHA-256 不变；保留处理前后两份 JSON，不覆盖原始失败证据。
2. 优先在备份的独立副本上验证启动与读取。真实 Host 启动会获取锁并可能把运行标为 interrupted，不能把这一步称为只读验证；也不能因可启动就自动继续或重放有外部副作用的运行。
3. 核对原有工作流／运行数、运行输入输出、附件可读取性、提案状态与库版本、规划快照和匹配代次日志的任务身份；未知项明确记录。确认无重复提交、没有新改业务定义后再结束维护窗口。
4. 如果出现引用缺失或新异常，停止写入，按同一备份整体或成对恢复相关证据；不要混用不同时间的 library/editor-state 或不同代次的规划快照／日志。保留失败处置记录供复核。

## 4、验证与后续合同

[专项测试](../../../../tests/storage-diagnose.test.ts)只使用 `/private/tmp` 合成目录；比较诊断前后的全部目录成员、普通文件字节、链接、inode、权限、大小、mtime 与 ctime，断言诊断打开的描述符均无写入、创建、截断或追加标志。覆盖历史孤儿与存在但损坏的所属运行、死／活／未知 PID、token 差异、链接、损坏与截断日志、F25 原偏移和隔离字节数、三组规划代次、F26 与正常后续编辑、权限异常、有界读取及 CLI 输出。短读由文件读取故障夹具确定性模拟；活 Host 的覆盖使用当前合成进程 PID，不构造真实 Desktop Host。

本轮没有读取真实 Desktop 用户数据，没有安装、发布或运行模型。全量构建／类型检查／测试的最终数字由交付报告记录；不能将合成夹具全绿写成真实用户数据恢复验收。

未来如要自动隔离或恢复，必须另立合同与测试：写入者停机或明确互斥、源文件及代次身份、跨文件一致性、保留原字节、持久化与 fsync 顺序、幂等回执、权限与链接边界、容量和失败中断、回滚、操作者授权、可见错误，以及恢复后禁止自动重放外部副作用。当前只读清单和维护规程不授权任何自动隔离、强删锁、日志截断或快照修复。
