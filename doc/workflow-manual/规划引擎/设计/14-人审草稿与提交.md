# 人审草稿与提交（T20）

## 1、问题

T05.7.9 实测的问候图按“读输入 → 生成内容 → **写入目标** → 回读验证 → **真人核对**”执行。真人点“不通过”时，只能走到 `review_rejected` 出口，写入早已发生：内容相同的文件也被原子重写，inode 已变。

这暴露两个问题：

- **拒绝撤不回写入。** 人审放在写入之后，审核只是“事后知会”，不是“把关”。
- **拒绝之后只能重来。** 图里没有修改环节，被拒的内容无法在原基础上改，只能整张图重跑。

## 2、原则：先草稿，审核通过再提交

借用 git 的思路：工作区改动先进入暂存区，审核后才提交。

| 阶段 | 做什么 | 拒绝时的影响 |
| --- | --- | --- |
| 草稿 | 把要写的内容写到本次运行专属的草稿位置 | 目标文件不变 |
| 审核 | 表单正文预填生成内容；审核人在表单中编辑，并填写修改意见。草稿文件只供查看，文件编辑不用于提交 | — |
| 修改 | 拒绝时带着表单正文和意见回到生成节点，以编辑后的正文为修改基础，再写草稿、再审 | 目标文件不变 |
| 提交 | 通过后把人审节点的类型化正文输出直接写到正式目标，不回读文件 | 只写一次 |

两条配套规则：

- **只有可撤回的动作能做草稿。** 文件写入可以先写到别处再搬过去；发 HTTP POST、发消息、执行 bash 命令一旦发生就收不回来，只能“先审核，通过才执行”。
- **提交前确认目标没被别人改过。** 从草稿到审核通过可能隔很久。审核循环前观察目标一次：已有目标精确 read，不存在的目标精确探测。提交直接使用 SDK 保留的版本观察做原子写入保护，期间不重读目标；重读会刷新观察、掩盖审核期间的外部修改。冲突时运行失败并显示 SDK 错误，不覆盖他人改动。

## 3、规则落在哪里

| 规则 | 内容 |
| --- | --- |
| 适用范围 | 新生成或明确修改的图；已有图不自动改写。没有人审关卡（至少两个操作按钮的人审节点）的图照常直接写入。 |
| 写入识别 | SDK 不提供工具“只读／会写入”的元数据。原生 write、edit 推定为**文件写入**；原生 bash、非 GET 的 HTTP 请求或 Swagger 操作推定为**不可撤回动作**；有已知操作合同的工具按合同。推定只用于把检查变严，永远不会因为名字把工具当成安全的，与 T18“不按同名放行”不冲突。其他未知工具不做推定，列为已知限制。 |
| 草稿位置 | 工作区内 `.dsh-drafts/{{sys.workflow_run_id}}/` 下，保留目标的相对路径。草稿在运行后保留，作为审核记录。 |
| 修改循环 | 草稿、审核、修改放进 `loop` 容器，轮数有上限（默认 3）；拒绝同时传递 note 和表单正文，超过上限停在 `not-approved` 出口。 |
| 编译期检查 | 有人审关卡的图中：人审之前的文件写入必须写在草稿位置；正式写入由所引用正文的关卡独占批准，正文来自其 paragraph 字段，字段 defaultValue 引用生成正文；目标观察位于 loop 前，loop 内不再观察正式目标；不可撤回动作必须在“通过”出口之后。违反时在同一轮给出具体路径和正确修法。 |

## 4、为什么由规划阶段生成结构，而不是运行时偷偷改写

另一条路是运行时自动把写入参数改到草稿目录。它对模型更省事，但等于在 SDK 之外改写工具调用，违背“不绕过 SDK、不暗中改参数”的约束，审核记录里也看不出发生了什么。

现在的做法用的全是现有节点：观察目标、写草稿、表单人审、提交，每一步都在图上可见，运行记录也逐一可查。代价是图会多几个节点。

## 5、验收

- 拒绝时：目标文件 hash、inode、mtime 都不变；草稿存在且内容是被拒的版本。
- 修改后通过：目标只写一次，内容等于最后一次批准的表单正文；修改草稿文件不影响提交正文。
- 审核期间目标被外部修改：SDK 提交失败，运行显示冲突错误，目标保持外部修改后的内容。
- 已有图（含 T05 问候图）不被自动改写；没有人审关卡的图行为不变。
- 离线回归之外，Desktop 实机运行一次：先拒绝一次，修改后通过。

## 6、实现边界（2026-10-22）

- 编译检查位于 `src/shared/planning-review.ts`，两种创作模式共用 `planningCandidateIssues`；约束新建或明确修改的图及受影响依赖。历史加载只记录内容诊断并阻断未提交候选，不改写旧图；存储和运行器不以此拒绝旧图，无关局部修改不强制迁移。无关卡的图行为不变。
- **历史记录按证据读取。** 新契约只约束新产生的候选；加载时发现旧候选不合新约束，记录诊断，已提交的候选保留原回执与发布状态，未提交的候选阻断发布，不能让插件整体启动失败。恢复先验证原子提交回执，再决定是否阻断；归属、摘要、交接和来源校验保持原有边界。历史优化报告及个人模板同样不以当前内容契约否定旧证据，模板实例化仍须通过当前校验。逐条豁免错误码会遗漏未来新增规则，每次收紧契约都可能再次破坏启动，因此不使用豁免名单。
- `reviewedFileWriteGraph` 使用现有节点：循环前精确探测目标；存在才 `native:read`，缺失直接进入审核循环。循环默认三轮：生成 → 写草稿 → human；human 的 `paragraph` 字段 `content` 使用 `defaultValue={{produce.text}}`，运行器以本次 run scope 展开默认值。拒绝经 assigner 把 `note` 和编辑后的 `content` 保存到 `vars.reviewNote`、`vars.reviewBase`，下一轮生成 inputs 同时接收两者。approve 直接调用 write，`content={{reviewGate.content}}`；成功后才设置 approved/stopped，超限返回 `not-approved`。human 语义查询按需提供指导与配方，不修改冻结 V4 Schema 描述或 compact-repair 基准请求。
- **表单设计已移除完整读取阻塞。** SDK 原生 read 的限长行窗口仍不能恢复精确文件正文，也不公开版本；现在它只用于建立 SDK 观察，不参与提交正文。审核正文来自 human 类型化输出并保存在运行状态，提交不再读回草稿、不再比较两个完整快照，也不依赖“可信完整读取工具”或因此转 needs-input。草稿保留供查看，提示明确说明“文件编辑不用于提交，修改须在表单正文中完成”。这不承诺保留原目标文件未展示的内容；生成器与审核表单决定整份新正文。
- **冲突保护由 SDK 原子操作负责。** 冻结的 `dsh-fs-observation-policy.js.txt` 以 `actor.agent.session` 为 owner，用 WeakMap 保存目标及版本；confirmed-present 选择 `replaceIfVersion`，confirmed-absent 或 unseen 选择 `createIfAbsent`。Host 的 `executeNative` 保留原对话 Agent 身份，通过 `RunObservationScopes.dispatch(runId,callId,...)` 将同一运行的调用隔离到该 run 的内存 ledger；人审暂停、回答和循环轮次沿用同一 ledger。已有目标在 loop 前读取一次，此后直到提交不重读，外部版本变化（即使内容相同）使 SDK 写入失败，目标不被覆盖。SDK provider 与 observation-policy 必须正常组合，本规则不授予工具权限或伪造注册合同。
- **首建与重启边界。** 首建使用精确 glob + 固定 `EXACT_TARGET_EXISTS_CODE` 的不存在分支，不无条件读取缺失文件；glob 本身不提供内容或版本观察。SDK 对 absent/unseen 都采用 `createIfAbsent`，因此首次创建受原子防覆盖保护，审核期间别人创建目标会拒写。SDK WeakMap 和 Host run ledger 均不落盘，Desktop 重启／策略热重载后观察丢失：若恢复执行，已有目标会退为 `createIfAbsent` 并被拒写；仍不存在的目标允许首建。不能声称“任意重启后一律拒写”，也不能自动补读来续写。Desktop 本身还可能把未完成 run 标为中断或要求恢复，本批未做实机恢复验收。
- **普通 tool 没有失败出口。** `workflow-semantics.ts` 与 runtime 仅为 iteration 提供 `errorMode`（单项失败的 terminate/null/remove），普通工具的异常会失败并终止 run，不会激活名为 error 的连线。因此本配方诚实保留 SDK 错误，不提供无法执行的 conflict 输出，不重读重试。成功输出仅在提交成功后出现。
- 静态检查要求对应草稿路径位于运行专属前缀下，后缀是无 `..` 的字面相对路径；提交引用批准它的同层 human paragraph 字段，默认值与对应草稿均引用同一生成正文。批准/default/reject/timeout 的旁路、缺少 loop 前的读取／精确不存在证明、loop 内重读目标、旧正文提交、拒绝丢失 note／正文、未批准却输出成功、重复提交都会报告具体修法。T18 已知合同检查复用原精确路径证明并允许人审 loop 继承入口观察；未知注册仍为未知，REVIEW 对 native ID 的结构检查不构成 T18 合同或授权。动态后缀、任意等价选择代码、跨容器间接传递批准及未知工具副作用仍不证明。
- 历史：`2dba2de` 的离线结构依赖完整草稿快照，未做 Desktop 验收；本次改为表单正文 + SDK 保留观察，解除该 read 阻塞。T20 保持未完成，下一步是安装新包、冷启动后新建图进行 Desktop 验收，已有 T05 图保持原样。

- 建议创建指令：“在当前测试工作区新建 T20 表单审核文件写入工作流，不修改已有 T05 图。目标 t20-review.txt；使用 template 生成固定初稿，修改时将 reviewBase 和 reviewNote 拼入正文，业务执行不调用模型。参考 human 语义中的 reviewedFileWriteGraph：loop 前精确探测目标，存在才 read；默认最多三轮；草稿写 .dsh-drafts/{{sys.workflow_run_id}}/t20-review.txt；审核表单 paragraph content 默认引用生成正文，注明文件编辑不用于提交；reject 同时保存正文和意见；approve 后直接把 human.content 写入目标，不再读取目标或草稿；SDK 冲突保留失败错误；超限 not-approved。保存为新图，先不要执行。”
