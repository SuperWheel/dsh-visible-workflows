## 1、方案结论与代码依据

采用“**精简创作表示 → Host 编译 → 完整校验 → 同一 author 内局部修复**”。首期保留 JSON 作为工具参数，以小型声明式 PlanSpec 表达业务设计；不引入另一个业务执行器，也不先建设通用 TypeScript 解释器。

“n8n 式”借鉴的是创作抽象、确定性编译和上下文连续性。n8n 的 CodeBuilder 将节点发现和代码生成放在同一个 Agent 循环，再把 SDK 表达编译为 Workflow JSON；它仍可能多轮调用模型。其 TypeScript SDK 前端使用 AST 解释器。本项目先采用可直接交给现有结构化工具的 PlanSpec，属于架构适配，不声称与 n8n SDK 同构。[CodeBuilder 源码](https://github.com/n8n-io/n8n/blob/master/packages/%40n8n/ai-workflow-builder.ee/src/code-builder/code-builder-agent.ts)、[SDK 解析器](https://github.com/n8n-io/n8n/blob/master/packages/%40n8n/workflow-sdk/src/codegen/parse-workflow-code.ts)

“Trustcall 式”借鉴的是保留失败对象、反馈校验错误、修补失败字段后重新验证。Trustcall 使用 JSON Patch 修复错误工具调用，并针对失败调用组织上下文。本方案在 TypeScript Host 内实现这一小部分机制，不引入 Python/LangGraph 服务。该机制减少重生成的机会，但真实延迟仍需实测。[Trustcall 源码](https://github.com/hinthornw/trustcall/blob/main/trustcall/_base.py)

必须区分两种失败：编译抛异常时，当前原始编辑对象没有被保留用于下一轮；编译已物化但未通过后续检查时，当前代码会把图放入内存 drafts。后者已有局部修复基础，本方案补齐前者，并避免每次换 child。

已有编辑工具本来就支持批量 edits。再包一层 batch 不能自动减少模型请求。改造重点是简化新建协议、减少必查目录、保留错误对象、把修复放回同一 activation。

### 1.2、已有证据及限制

历史 R3 与 R5 的 author/optimizer 结构化参数从 14,689 字节降至 12,792 字节，模型步骤却从 7 增至 13，界面耗时从 207 秒增至 290 秒。R5 单字段修改记录为 25 秒、一个 child、一个模型步骤。这些是个案，版本与执行条件并非严格对照，不能据此估计本方案能提速多少。[现有验收记录](../17-局部编辑意图与宿主编译.md)、[耗时分析](../../../../docs/evidence/v002-merged-install-20261018/planning-efficiency.md)

不以 JSON 字节数下降作为成功条件，也不预先把本地 child 创建、JSON 解析或 Graphon 判定为主要瓶颈。需要分别测模型请求、等待准入、工具查询、编译、存储及回归。

~~~mermaid
flowchart TD
  A[已有规划入口与冻结上下文] --> B{来源}
  B -->|普通设计或修改| C[准备紧凑创作上下文]
  B -->|已完成对话或 verified-trial| D[现有证据校验与方法提炼]

  C --> E[一个 author activation]
  E --> F[structured_output 提交 PlanSpec 或编辑意图]
  F --> G[保存受限原始草稿并确定性编译]

  H -->|可修复| I[字段诊断及最小相关片段]
  I --> E
  H -->|有效| J[原生结构化输出提交成功并结束 child]
  H -->|权限或版本冲突| X[现有阻断终态]
~~~

表 2-1 设计选择：

| 选择 | 首期采用 | 理由 |
| --- | --- | --- |
| ✅ 声明式 PlanSpec + Host 编译 | 是 | 可用当前结构化工具；省去重复操作字段、身份和框架字段 |
| TypeScript 风格 SDK + AST 前端 | 后续独立实验 | 只有在 PlanSpec 数据表明语法仍是瓶颈时再做；不能默认文本代码更快 |
| 对当前标准 Workflow 做通用任意 JSON Patch | 否 | 修复面过宽；补丁只作用于创作草稿，最终图由 Host 物化 |
| 取消全量校验，改成只验改动字段 | 否 | 当前图规模下先保留正确性；裁剪的是模型上下文 |
| 合并 distill、author、optimizer 成一个万能 Agent | 否 | 证据提炼、业务设计、优化权限不同；首期只统一 author 的发现、提交和修复 |
| 更换 JSON 交换格式或 Graphon | 否 | 当前问题是交互与重试结构，现有执行合同继续复用 |

主要目标路径：相关节点合同已在首轮上下文时，合法候选只需一次 author 模型响应；遇到一组可修复错误，再用一次响应提交补丁。目录未知、业务复杂或证据不足时允许额外调用，不承诺所有工作流固定一轮完成。

## 3、精简创作接口

以下接口、字段及函数均为拟新增合同，不能用于调用当前插件。对外仍使用现有 plan/get/answer/cancel/publish 入口，不要求主 Agent 再设计一遍图交给 author 重写。

### 3.1、任务绑定与入口拆分

Host 建立 AuthorSession：

- 绑定 taskId、childId、原始 workflow revision/digest、目录 digest、权限范围与来源摘要。
- 绑定已有节点的稳定短名，如 n1、n2；新增节点用可读 key，如 format。同一任务删除节点后不复用短名。
- 模型侧不填写 UUID、baseDigest、workspaceId、budgetDecision、executionPolicy 或时间戳。版本冲突检查继续在 Host 进行。
- 内部传输版本记为 authorProtocolVersion=2，由 Host 的任务路由确定；不是 Workflow 的 formatVersion。
- Host 按 create/revise 选择较小的输出 schema；每个 schema 只包含该初始提交、repair、needs-input 三种分支，避免所有操作平铺成可混填的大对象。

实际工具参数统一为 `{submission: ...}`。当前 SDK 要求工具 schema 根为 object，而且同一 schema 节点不能同时声明 type 与 oneOf；因此三个模式的 oneOf 放在 submission 属性内部，不能直接放在 object 根。第 3.2、3.3、5.2 节的提交示例包含这个外层；修复路径相对于 Host 提供的 repairDocument，而非外层工具参数。

省略 baseDigest 的前提是该工具仅存在于本次受控 child 中，执行时使用绑定快照。未来若开放无状态外部接口，必须另带可信任务句柄与期望版本，不能照搬省略规则。

### 3.2、新建：一次描述业务图

~~~json
{
  "submission": {
    "mode": "create",
    "title": "姓名问候",
    "nodes": [
      {
        "key": "start",
        "kind": "input",
        "config": {
          "fields": [
            {
              "name": "name",
              "label": "姓名",
              "required": true,
              "type": "text"
            }
          ]
        }
      },
      {
        "key": "format",
        "kind": "template",
        "config": {
          "text": "你好，{{input.name}}！"
        }
      },
      {
        "key": "result",
        "kind": "output",
        "config": {
          "text": "{{format.text}}"
        }
      }
    ],
    "chains": [
      {
        "key": "main",
        "nodes": [
          "start",
          "format",
          "result"
        ]
      }
    ],
    "coverage": {
      "R1": [
        "format",
        "result"
      ]
    }
  }
}
~~~

模型只声明节点和业务配置。Host 展开 chain、分配身份、补充可确定的默认值、编译引用，并生成 canonical PlannerOutput。可省略的 description、summary、assumptions、title 等说明字段采用明确默认；不默认业务参数、需求覆盖、证据和工具权限。

具体语义：

| 字段 | 合同 |
| --- | --- |
| nodes | 声明列表，每项含 key、kind、config，title/scope 可选；config 字段继续来自当前节点 schema |
| chains | 声明列表，每项为 {key,nodes:[节点key]}；连续节点展开为无 port 连线，只用于允许默认出口的节点 |
| links | 显式连线列表，每项为 {key,source,target,port?}；if/classifier 等分支按当前出口语义填写 |
| scope | 容器 key 路径，最多五层；所有连线端点必须同层。容器 body 由 Host 组装，模型不直接替换 config.body |
| roles / environment | 带 key 的声明列表，只含已有合同允许的角色与变量；使用同一符号表体系；Secret 只允许声明，不含值 |
| coverage | 以 R1 和已冻结 procedure step ID 为键，值为相关节点 key 数组；模型必须作真实映射 |
| 引用 | {{format.text}} 等只在运行时支持引用的 config 路径解析；input/env/sys 和模板局部变量保留各自语义 |

创建基线当前由 makeWorkflow() 产生一个 input、一个 output 和直连边。Host 将 start/result 绑定到这两个预留节点，替换未发布新图的业务投影，不能同时保留旧直连边形成意外旁路。该替换语义只适用于 create；已有 workflow 仍走局部编辑，不能使用 create 重建。

key 在一个任务内唯一，禁止危险键及保留命名空间；角色、环境变量和节点使用分离的符号空间。chain 与显式 link 重复时可以去重完全相同的声明；不同出口、跨 scope 或冲突定义返回错误，不能猜测连线。

coverage 的 schema 由 Host 生成所需键；修改已有图时可列出已有节点选项，新建 key 在提交后校验存在性，不能提前假定已知。Host 只提供需求键和空白骨架，不能自动认为每个步骤已被覆盖。requiresReview 仍须映射到 human，并通过现有依赖与来源检查。

**SDK 子集适配：** 当前 ObjectJsonSchema 只接受 boolean additionalProperties，不接受带 schema 的 additionalProperties 或 patternProperties。初始 nodes/chains/links 因此使用有固定字段的列表，不能把 z.record 的完整 JSON Schema 原样交给 SDK。Host 在收到可索引声明后生成 nodesByKey/chainsByKey/linksByKey 修复视图，使修复不依赖变化的列表下标；动态 coverage 键则可以用本任务已知的 properties/required 表达。线上 wire schema 与 Host 严格 schema 分工明确，并分别测试；字段长度、深度及资源上限仍由 Host 强制执行。

### 3.3、修改：保留局部操作，缩小表达面

单字段修改使用按节点聚合的输入，避免重复 op/node 和同一节点多次操作冲突：

~~~json
{
  "submission": {
    "mode": "edit",
    "updates": {
      "n2": {
        "set": {
          "text": "你好，{{input.name}}，欢迎回来！"
        }
      }
    },
    "coverage": {
      "R1": [
        "n2"
      ]
    }
  }
}
~~~

updates 的可用节点键由 Host 动态生成固定 properties，不使用 SDK 不支持的类型化动态键。set/unset 只对应 config 顶层字段，未指定的字段保留；kind/title 单独声明。新增、删除和连线分别使用 addNodes/removeNodes/addLinks/removeLinks，role/environment 变更沿用等价的受限语义；新声明使用第 3.2 节的列表格式。数组和映射的普通 set 仍整体替换，深层修复由第 5 节补丁处理。

Host 将对同一节点不同字段的更新合并成一次现有 update-node。设置与删除同一字段、删除后更新、修改范围外节点均拒绝。不通过默默“最后一次覆盖”解决冲突。

首期不增加主 Agent 直接写图的第二条保存入口。将来如果证据表明主 Agent 已能提交可靠结构化修改，可独立评估省掉 child 的受控直通路径，但仍要经过同一编译与发布检查。

### 3.4、两遍编译算法

1. **声明遍历**：冻结输入对象，检查大小、深度、key、重复声明和资源上限；建立任务级符号表，为新 key 从 Host 池预留稳定身份。可唯一索引的列表转换为按 key 定位的创作视图，保留未知字段供严格校验拒绝，不能靠归一化丢弃错误。
2. **结构展开**：展开 chains/links，按 scope 建子图；先声明容器再加入其子图；复杂分支不自动猜测出口。
3. **引用绑定**：复用当前 rewriteConfig 的路径白名单和模板词法处理，输出标准稳定 ID 引用。仅替换已解析的引用 token，不替换代码、引号字面量或普通业务对象的同名字段。
4. **降级为现有编译输入**：生成 PlanningEdits，并由 Host 填 baseDigest、@ref/+key、coverage canonical 字段。对重复字段更新先合并，依赖决定操作顺序，不要求模型手排。
5. **物化与验证**：调用现有编译核心、materializePlanningCandidate、planningCandidateIssues 和 coverageIssues。保存“创作路径 → 编辑操作 → 图节点/配置路径”的定位映射。
6. **接受**：只有全部必要检查通过的 canonical Workflow 可成为 task.candidate；后续 readiness、来源检查、Graphon 回归与发布仍沿用现有路径。

需为 compilePlanningEdits 增加仅 Host 可传入的身份分配上下文，或抽出共用编译核心，使同一个 key 在补丁重编译时仍绑定原 ID。不能每轮根据对象当前顺序重新分配身份。相同草稿重复编译必须幂等；移除 key 后该身份在本任务内不再分给另一 key。

所有修复从“初始可信基线 + 当前创作草稿”重新编译，避免对上一轮已执行的 edits 再执行一次造成重复节点。正常单节点 revise 仍可直接使用现有编译路径。

声明解析、索引、连线展开为线性遍历；影响范围通过邻接表和引用索引计算。这里没有求全局最优图编辑距离，也不需要 CRDT。完整现有校验可能有额外遍历，不能据此笼统宣称整个编译器都是 O(V+E)。

## 4、减少首轮目录请求和上下文

### 4.1、上下文准备算法

新增 buildAuthorContext()，仅执行确定性读取：

1. 给出全图结构索引：稳定 key、kind、title、scope、输出合同、连线及固定标记。
2. 对 targetNodeIds 或明确新增相关节点，给出完整可编辑配置；读取其引用的上游输出合同、直接边界和下游受影响约束。
3. 利用当前节点类型、procedure 和已有真实 tool ID 预取语义；采用目录原有精确匹配/关键词检索，不增加一个“帮忙选节点”的模型调用。
4. 当前语义词典中的相关字段、输出、示例直接注入；规则改为“已经提供准确合同即可提交，缺失时再查询”。
5. 工具目录先给相关项和可查询索引，不每轮列出最多数千个工具；真实 inputSchema 仍可按 ID 获取并在 Host 全量验证。

目标建议：首轮上下文准备后，已知三节点纯模板场景目录工具调用为零；常见组合一次查询批量补齐所缺合同，不强迫模型按节点逐一问。

### 4.2、裁剪不能掩盖依赖

目标完整 config、数据引用闭包、同层分支和人工检查边界优先保留。大型无关 prompt/code 正文可返回字段摘要及精确读取句柄；不得截断正在编辑的字段而不标注。

增加仅限当前冻结任务的 planner_context_read(keys, fields)，不能读任意文件、其他会话或其他任务。token/字节超过首屏上限时明确返回 omitted 列表；若正确修改必须扩大上下文，允许读取，不能因追求体积目标丢掉实际条件。

引用闭包无法安全确定时扩大到相关 scope，必要时使用完整图。无论模型看到多少上下文，Host 都用完整图检查输出类型、范围、固定节点和引用关系。跨任务缓存仅允许公开静态语义，按合同版本/摘要失效；含业务内容的任务上下文不共享。

## 5、Trustcall 式局部修复

### 5.1、保留原始失败对象与最佳候选

新增内存 AuthorDraft，内容分层：

~~~typescript
type AuthorDraft = {
  protocolVersion: 2
  revision: number
  rawSubmission: unknown       // 有限大小的普通 JSON；不授予任何权限
  rawDigest: string
  repairDocument: unknown      // 可索引时为按 key 组织的等价视图，否则保留原对象
  repairDigest: string
  symbolTable: HostSymbolTable // Host 管理，不由模型 patch
  issues: RepairIssue[]
  submissionCount: number     // 初次提交与修复总计最多 3 次
}

type RepairIssue = {
  code: string
  sourcePath?: string         // JSON Pointer；不能定位时明确缺失
  nodeKey?: string
  message: string
  repairClass: 'field' | 'structural' | 'needs-input' | 'fatal'
  allowedPaths: string[]
}
~~~

以下对象不可混用：

- rawSubmission：可能错误的创作输入，保留原始提交供诊断；repairDocument 是应用补丁的对象，与原始输入保留可追溯映射。
- compiledDraft：已物化、尚未完全验证的中间图。
- task.candidate：已通过接受条件的合法候选；优化失败时保留。
- 来源与权限材料：原始冻结上下文，不在补丁对象中。

原始草稿首先经过普通 JSON、大小、深度、危险键检查；这些安全检查失败不保留对象用于模型修复。不得把未经验证的 rawSubmission 传给存储、运行器或发布入口。

普通 preview 仍为内存数据。首期不持久化完整 rawSubmission；用户补充信息后的新 activation 可携带必要草稿及补充答案，但进程重启后标 interrupted，不能自动重启模型。verified-trial 的现有恢复日志和来源摘要继续按 R7 合同处理，不能借持久化草稿提升试做可信度。

### 5.2、字段级反馈与补丁示例

假设模型在 result 节点误写了 {{format.result}}，模板实际输出 text，Host 返回：

~~~json
{
  "status": "repairable",
  "draftRevision": 1,
  "issues": [{
    "code": "INVALID_REFERENCE",
    "sourcePath": "/nodesByKey/result/config/text",
    "message": "format 的输出字段是 text",
    "allowedPaths": ["/nodesByKey/result/config/text"]
  }],
  "fragments": {
    "/nodesByKey/result/config/text": "{{format.result}}"
  },
  "contracts": {"format": {"outputs": {"text": "string"}}}
}
~~~

模型下一次调用同一个 structured_output：

~~~json
{
  "submission": {
    "mode": "repair",
    "draftRevision": 1,
    "patches": [
      {
        "op": "replace",
        "path": "/nodesByKey/result/config/text",
        "value": "{{format.text}}"
      }
    ]
  }
}
~~~

只提交补丁，不重报 nodes、chains、正确的覆盖映射或框架字段。所有可独立修复错误在同一反馈批次返回，避免一次模型响应只修一个字段。缺失 key、重复 key 等导致对象不能唯一索引时，repairDocument 暂保留原对象并提供精确数组路径；修复后才构造稳定 key 视图，草稿 revision 随之递增。每次以 Host 最新反馈路径为准。

### 5.3、补丁事务

- 首期允许 RFC 6902 的 add/replace/remove 子集，外加明确命名的 replace-text 扩展；不声称整个协议严格等于 RFC 6902。
- draftRevision 必须匹配；Host 另外比较绑定 repairDigest 和原始 rawDigest。补丁在 repairDocument 副本上按序应用，任一失败则整批回滚。
- 路径使用 JSON Pointer 解码后逐段校验。禁止根对象替换、危险键、Host 身份、权限、预算、来源和证据记录路径。
- 只开放诊断及必要依赖修复集合；若修复需要新增连线或节点，Host 根据图错误开放相应结构路径，仍受原请求范围限制。
- 正常修复视图中的 nodesByKey/linksByKey/coverage 使用稳定 key；内部数组修复可整字段替换。若使用数组索引，必须绑定当前草稿版本，执行顺序可验证，不能把旧下标用于新数组。
- replace-text 只用于 prompt/text/code 等已获准字符串字段；find 必须恰好匹配一次，否则报歧义，不默认模糊匹配或 replaceAll。
- 每批补丁后重新编译并完整校验；只验 patched 字段不足以发现引用、分支和输出合同回归。
- 每任务初次提交加修复最多三次；无变化补丁、重复的草稿摘要与同一组错误停止循环。达到上限保留诊断，不自动退回完整图重写。

修复只需局部输出，Host 初期仍可完整重编译。只有测量证明本地编译占比显著，才增加依赖索引驱动的增量校验；最终接受前保留全量检查。

### 5.4、错误分流

| 错误 | 处理 |
| --- | --- |
| 缺字段、错字段类型、错误引用、coverage 遗漏、工具参数不符 | 定位到创作对象，批量局部修复 |
| 错分支出口、缺必要连线、必须增加 human | 开放最小相关结构路径，重新验证图语义和原范围 |
| 无法解析的 JSON / provider 未提供可用对象 | 不能对不存在的树做 Patch；允许在总提交上限内重交精简创作输入，明确记录 fullResubmission |
| 缺少业务输入、需求相互冲突 | needs-input，使用现有原生询问流程 |
| 工作流 revision、目录或来源摘要冲突 | 进入现有 conflict/blocked 路径，不让模型猜新版本 |
| 固定节点、越权修改、Secret 值、宿主元数据修改 | 终止本次写入，不当作可自动消除的普通字段错误 |
| provider 错误、清理失败、用户取消、readiness 基础设施失败 | 仍按当前专门终态处理，不追加修复模型请求 |
| 优化缺少可信回归证据 | 保留合法基线；不能用模型生成 expected 值填补来源缺口 |

## 6、同一 activation 内完成提交和修复

### 6.1、已核对的 SDK 接入条件

当前 PlanningSubagentService 只封装 startActivation/result/dispose，没有公开的本地 resume 合同，因此不设计为“先结束 child 再强行续聊”。

已安装 SDK 0.2.1-rc.1 的 tools/execute 允许围绕工具执行；structured_output 的原生实现先验证参数，再调用 concludeTurn，并在最终 tools/result 成功后捕获结果。模型侧校验失败可以保持 child 继续。因此可以在原工具执行前接入本项目校验。

本地核对位置为 dsh-tools/lib/types/index.d.ts 的 tools/execute、tools/result，以及已安装 dsh-subagent 的 attachStructuredRuntime。官方同类设计说明见[结构化输出与最终结果提交](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/archived/architecture/2026-07-12-agent-scope-runtime-design.md)。安装版与未来宿主版本须单独验证，不能只根据最新文档认为生产可用。

### 6.2、提交门控算法

拟为 author 增加独立受控驱动，复用现有生命周期、准入、计量和 guard：

~~~text
on structured_output execution for this exact child:
    recheck cancellation + authority + bound snapshot
    serialize submissions within this AuthorSession
    parse initial submission or apply patch to retained draft
    compile against original trusted baseline
    validate full Workflow + scope + coverage + required provenance

    if fatal:
        stop through existing failure path
    if repairable:
        retain bounded draft and issue mapping
        return ordinary tool error with repair packet
        do not invoke original structured_output body
    if accepted:
        stage canonical result keyed by immutable execution token
        call next() to run the native structured_output body

on immutable tools/result for the same execution token:
    if final result succeeded:
        commit staged canonical result
    else:
        discard stage; policy/cancellation failure cannot become accepted

after activation settles:
    require native completed result AND committed canonical result
    return canonical result to service
    dispose and await cleanup; cleanup failure retains precedence
~~~

错误反馈必须发生在原生工具 concludeTurn 之前。不能先让 structured_output 成功，再在 post-execute 中返回业务错误而假设一定会恢复循环。不能修改不可变 exec.args，也不能伪造工具最终成功结果。

有效提交直接通过原生结构化结束机制完成，无需另设“validate → 请再调用 finish”的模型回合。最终 SDK 捕获的参数可能是 repair 信封；service 使用 Host 提交的 canonical result，并核对它与同一 execution token/最终参数摘要绑定，不能把补丁信封再当旧 PlanningEdits 编译。

schema 同时接受本轮初始模式、repair、needs-input；首个失败草稿出现后禁止重做任意初始提交，只有确实无法取得 JSON 树的语法失败才允许受限重交。原生工具说明中“只调用一次”需在该 child 的提示组装中精确调整为“失败可修补，成功终止”，保留宿主政策与真实结束语义。

### 6.3、限制与门槛

- 不增加业务工具、文件、网络、run_code 或委派权限；author 仍只读元数据。
- beforeStep 在每次真实模型请求前生效；修复沿用总步数、用量、取消、闲置超时和总时长保护。
- candidateAttempts 迁移为提交次数时覆盖同 child 中的失败提交，不能直到 child 结束才计数。SDK 参数拒绝也要从对应调用结果计数；没有可用参数树的语法失败保留事件归属，受同一请求/提交保护，不能在统计之外无限重试。
- 线上单任务最多 24 步、8 个 child、每 child 8 步和 20 分钟总保护暂不提高；新路径不能靠扩大预算制造成功率提升。
- 工具提交串行化；同一模型响应出现两个提交时，第二个不得越过已接受结果或使用过期 draftRevision。
- 最终结果遭 post-policy 拒绝、用户取消、权限撤回、dispose 失败，均不得上报 ready。
- 先验证真实 SDK 的“无效提交 → 一次补丁 → completed”路径，再接入正式服务。若宿主能力不符，保持旧路径，不能静默改用另一个 Agent 运行框架。
- 同一个 child 不等于一次模型调用，也不保证减少输入 token；保留历史可能增大上下文，必须测实际请求与用量。

## 7、与优化及 R7 试做链路的衔接

### 7.1、证据来源

精简 author 接在已验证的 PlanningContext/TaskProcedure 之后，兼容普通设计、current-conversation 和 verified-trial。R7 当前还在变动，实施时对 trial、trialTask 以及各 digest 的实际最终合同逐项对齐。

不重做已经有可信回执的原任务，不把没有来源的 PlanSpec 升级为已验收业务。原 provenanceDigest、sourceMap、requiresReview、readiness、发布前来源复核均保留。

### 7.2、optimizer 分第二步接入

先验证 author 的效果，再把同一“原始输出保留 + 局部修复门控”接到 compileOptimizationEdits。optimizer 仍只能改允许的 kind/config、替换理由与证据选择，不能使用 author 的拓扑编辑权。

优化草稿绑定当前最佳候选摘要和对应来源摘要。错误的 evidenceCase 字段可以修补；expected/upstreamOutputs 仍必须引用完整且成功的原记录，不能把局部字段自动升级成可信根结果。

优化策略轮数与格式修复次数分别计数。首期保持最多两次优化提交；一个格式修复也占用提交次数，不在原两轮之外再乘以三次修复。旧基线在任何未通过的优化中保持可用。

Graphon 继续执行当前允许的记录样本片段回归，比较原输出合同、人工节点和累计替换影响。author 校验成功与 Graphon 片段成功均不等于生成图已经完成全业务执行。

顺序采用 **P0 → P1 → P2 → P3/P4**。先修“错误对象丢失和换 child”，有单独收益证据后再判断精简创作语法的增益。P1/P2 分别保留实验开关，不能只比较整包新旧而不知道哪个改动有效。

## 9、验证实际提速的对照测试

### 9.1、主要假设与实验组

表 9-1 四组因子实验：

| 组 | 创作接口 | 纠错方式 | 作用 |
| --- | --- | --- | --- |
| A | 当前 PlanningEdits | 当前换 child、用新视图继续生成 | 对照 |
| B | 精简 PlanSpec / EditSpec | 与 A 同类的结束后再生成 | 测精简接口整体效果 |
| C | 当前 PlanningEdits | 保留失败对象、局部 Patch、同 activation | 测局部修复整体效果 |
| D | 精简 PlanSpec / EditSpec | 保留失败对象、局部 Patch、同 activation | 目标方案 |

“精简接口”因子含稳定引用、Host 绑定和上下文预取；“局部修复”因子含失败对象保留和同 child 修复。四组只能归因到这两个机制组合，不能把全部收益都说成 JSON 字段变短或 child 复用的单项效果。需要进一步解释时，再对 D 单独禁用预取或同 child 连续性做消融。

常规无错误路径也必须测试：D 不能为获得草稿句柄而多调用一次模型，不能为返回成功再要求一次确认。另记录 A0：没有实验额外限制的冻结当前生产策略，用于最后 A0/D 的用户体验核验。

新建仍需表达完整业务拓扑和实际 prompt/code 内容，PlanSpec 只是省掉机械操作与框架字段，不会让这些业务信息消失。若 C 已有稳定收益而 B/D 增益不足，就优先启用局部修复、保留精简接口为实验策略；最终选择由数据决定。

| S03 | 冻结可信 verified-trial 上下文 | trial 归属与所有来源摘要不变，不重做试做 |
| S04 | 有完整记录样本的确定性优化 | 合法基线保留，优化与 Graphon 回归范围正确 |

correctness oracle 独立于被测编译器：同时包含目标字段断言、允许修改集合、业务不变量、分支/依赖断言、参数替换后的预期结果。不能用“同一个校验器返回 ready”作为全部质量标准。

纯模板/code 用合成输入经真实 Graphon 执行，并清楚标为合成业务样本。含模型/外部工具的场景使用固定合同断言、冻结真实记录及盲评量表；替身只能证明接线与合同，不能证明开放式业务结果真实正确。盲评记录失败原因，不额外引入一个 LLM 裁判替代明确断言。

最终导出经当前 JSON 导出/导入往返；比较时仅为图匹配规范化 Host 分配身份、时间和布局，不忽略字段、分支、人工检查、预算或来源差异。revise 的未修改实体直接要求原值一致。

另设拒绝与恢复组：固定节点修改、Secret 值、越权字段、过期草稿、目录变化、来源变更、取消、超时、post-policy 拒绝、dispose 失败、重启恢复。这些不是“成功生成用例”，不能把快速拒绝混入生成耗时计算。

### 9.3、分层执行，避免把模拟速度当成真实速度

1. **确定性测试**：固定初始输出和错误补丁，验证编译/修复/生命周期；没有真实模型调用。覆盖全部协议规则与旧回归。
2. **受控错误实验**：给所有相关策略同一份含单一已知错误的创作对象及同等错误信息，比较完整重新提交与局部补丁所需的真实模型调用、时间和正确率。错误涵盖错误引用、coverage 缺项、工具参数、分支和长文本；结果单列为注入错误实验。
3. **自然生成实验**：从自然语言请求开始，各组模型自由生成，记录实际出现的错误和修复；这是主要性能证据。
4. **全链路实验**：从用户请求到最终 ready/预览可见，包含提炼、优化、Graphon、清理和工具返回。用于验证阶段提速是否真的改善体验。

author 因子实验冻结同一 TaskProcedure/证据输入，以排除前置提炼随机性；不能把该结果称为完整链路提速。全链路实验重新计算前置成本；执行优先场景另外报告 trial 执行与人工等待，并与相同执行策略比较，不能只在 D 中跳过试做。

### 9.4、实验条件与样本量

- 固定源码快照和文件 manifest；A/B/C/D 使用同一实现包的策略开关、相同校验器和冻结目录。A0 另保存原生产快照。记录 commit 不足以代表带未提交修改的工作区。
- 固定 provider、具体 model 标识/已知修订、effort、输出上限、区域、宿主版本、Graphon 版本、fixture 和 schema 摘要；温度/seed 仅在 provider 支持时固定。模型后台版本未知就标未知。
- 使用独立临时工作区和任务身份，顺序运行配对区组，不与其他压测并发；组顺序按用例轮换并随机化，避免总让 A 先跑。
- 缓存条件相同；明确冷/热条件及 provider 报告的 cached tokens。无法关闭的服务端缓存不声称已清空；不得只给 D 预热。
- 机制比较统一 author 阶段最多八次模型请求、三次提交；A/B 的八次跨其重开的 child 累计。此额外阶段上限须披露，不假装完全等同当前线上策略；全链路 A0/D 另按现有生产上限核验。
- 先做 16 用例 × 2 重复 × 4 组 = 128 次自然生成探索，修复与拒绝组单列。该批用于筛选，不据此证明小幅成功率差异。
- 正式比较使用另外冻结的至少 24 个留出用例 × 5 重复 × A0/D 两组 = 240 次。按任务类型均衡扩展上述语料，跑前锁定期望和阈值；探索语料结果另列。
- 正式实验不得一边观察显著性一边无限加样本。若质量非劣置信区间或尾延迟不足以判定，报告不确定，依据探索方差预注册下一批独立验证。
- 成本先按探索得到的真实用量估计；未知 token/费用保留未知。此处设计真实调用量，不在本次文档任务中自动执行。

### 9.5、逐请求指标与时间归属

表 9-2 必采指标：

| 指标 | 口径 |
| --- | --- |
| T_user_ready | 用户请求发出至正确 ready/预览返回；主 Agent 后处理和 UI 可见延迟能测则单列 |
| T_planning_ready | Host 接到规划请求至正确候选完成 readiness、按相同策略优化、清理并返回 |
| T_author_valid | 冻结 author 输入完成至首个经独立 oracle 判定正确的候选 |

| schemaFailures / semanticFailures | 工具参数、创作编译和图业务检查分开计数 |
| fullResubmissions / patchSubmissions | 完整重新提交和局部补丁分别统计 |
| firstPassSuccess | 首次提交通过完整检查且独立 oracle 正确的比例 |

在现有 beforeStep/onUsage 基础上扩展请求关联，按 taskId/childId/turn/step/attempt/事件 seq 去重。session 中晚到的用量仍属于原调用，不能被清理时丢弃。原计费账本与性能 trace 分离，不为了压测降低存储耐久性。

每次运行保存：run 配置、完整来源摘要、各阶段 span、逐请求时戳与回执、脱敏初次输出/补丁、错误代码、最终标准 Workflow、独立 oracle 结果。日志仅限隔离 fixture，不收集真实 Secret 或无关会话。报告必须能追溯至某个 run，而不是只有汇总表。

### 9.6、分析方法与发布门槛

同时报告四项结果：

1. 全部尝试的成功率、失败类型和单位总时间的正确完成数。
2. 每个留出任务的配对耗时比，以及按任务等权汇总的中位数；用按任务聚类的配对 bootstrap 给出 95% 区间，重复运行不能当作完全独立任务。
3. 双方均成功的条件耗时，以及将失败/超时按共同任务 deadline 计入的惩罚耗时。两者都报，防止用失败更快制造提速。
4. p50/p95、实际模型请求数和纠错次数；尾部样本不足时将 p95 标为描述性结果，不宣称已证明尾延迟改善。

预先建议的切换默认门槛，实施前可根据成本与业务重要性调整，但不能看完结果再改：

- 安全、来源、范围、JSON 往返、Graphon 合同的确定性门槛全部通过；不能牺牲这些规则换速度。
- 正确完成率差值 D−A0 的 95% 区间下界高于 −5 个百分点；若样本不够证明则保持实验开关，不写“质量不下降”。
- 留出集配对 T_planning_ready 中位数至少降低 20%，且改善区间排除零；T_user_ready 同方向，不能只有 author 局部快。
- 单字段修改不得出现额外确认请求；其配对中位数不超过 A0 的 1.10 倍。长文本与复杂图分别报告，不能被简单案例平均掉。
- 观察到 p95 恶化超过 10% 或新增长尾循环时阻止默认切换，先定位；尾部证据不足则补充独立验证。
- 总模型请求或修复重生成应有可解释下降；如果只减少字节而等待不降，判定未完成提速目标。

20%、5 个百分点和 10% 均是本方案建议的验收阈值，不是现有结果或开源项目承诺。
