核对日期：2026-10-30。对象：v0.0.2 r58（提交 `0224200`；草稿组装始于 `5bdfc26`）。设计见[设计 26 §6](设计/26-照试做搭骨架.md)。

## 1. 解决什么问题

r36 A 用上骨架后，作者仍思考了约 8.5 分钟。思考内容主要是模板写法、开头参数、状态码分支、回读核对和检查代码，都是骨架 `open` 里留给作者的部分。这些部分其实也能从试做证据确定下来。

所以 Host 在骨架之外再补齐这些部分，生成一份完整的 create 提交，叫 `trialSkeleton.draft`。草稿先用同一编译器检查一遍，通过了才交给作者。作者核对后可以原样提交，也可以按需求修改。

## 2. 节点链

```text
start → fetch → fetchOk → select → [lines] → render → save → check → result
                                       └─ line（迭代内的一行模板）
```

| 节点 | 内容 | 来自 |
| --- | --- | --- |
| `start`（input） | 参数 `url`（多个网址时还有 `url2`…）和 `outputPath`，默认值取试做用过的值 | 试做调用 |
| `fetch`（http） | 网址改为 `{{input.url}}`；值等于该网址的 `baseUrl` 一并改为参数 | 骨架 |
| `fetchOk`（code） | 状态码不是 2xx 就报错停止，节点名写“确认抓取成功” | Host 固定代码 |
| `select` / `extract` | 骨架原样；`limit` 缺失时补成反推得到的条数 | 骨架 |
| `lines` + `line` | 只在需求要求“逐条用同一模板”时出现，见第 3 节 | 反推 |
| `render`（template） | 反推出的模板；反推失败时为占位 | [反推](23-写出文件反推渲染模板.md) |
| `save` | `verified-file-write@1.1.0`，target 为 `{{input.outputPath}}`，content 为 `{{render.text}}` | 骨架 |
| `check`（code） | `trialTask.artifacts` 的文本包含检查、`save.check === 'window-match'`；反推成功时再加条数检查，并逐条核对记录（见下） | Host 固定代码 |
| `result`（output） | 按节点逐行写：每个网页抓取的状态码和字节数、抽取条数，再接核对结论、输出路径、写入核对结果 | Host |

**逐条核对（T35）。** 列表模板原样输出（不经 replace、lower 等改写）的字段，试做抽到的每条记录都要满足：值非空、链接字段是完整网址、写出的正文含有这个值。只挑一个标题字段，加上全部链接字段。这样需求里的“写入后回读核对”“告诉我每个节点的结果”在草稿里就已经做到，作者审核时不用再自写核对代码或重写 result。r57 C 作者为这两件事多写了约 1.4 万 token。

每个节点都只做它名字说的事，没有隐藏行为。

## 3. 逐条套用同一模板

需求或过程说明里出现“逐条/逐个/逐项……模板/生成/套用”，或“用/套同一个模板”时，把整理拆成两个节点：

- `lines`：迭代节点，逐条处理 `select.items`，内部放一行模板 `line`。
- `render`：只负责合并，并补上序号：`{% for row in lines.result %}{{loop.index}}. {{row}}\n{% endfor %}`。

只有反推出的模板每条恰好一行时才拆。否则保持单个 render 循环，由作者决定。

## 4. 覆盖关系

过程（procedure）每一步都引用了试做证据。Host 把每条证据对应到现在承担它工作的节点：

- 写入 → `render`、`lines`（如有）、`save`；
- 产物的探测和回读 → `save`、`check`；
- 对应不上的步骤 → 覆盖全部节点。

`R1`（整体需求）覆盖除 `start` 以外的全部节点。

## 5. 先编译再交出

Host 用和作者提交时完全相同的编译器、模板绑定和覆盖检查，把草稿提交一遍：

- 通过：作者提示里只给 `draft`、`sources`、`open` 和说明。草稿可以原样提交；提交时要保持结构，模块留在 `modules`、节点留在 `forms`，不添加草稿里没有的属性。
- 不通过：保留草稿，把这次编译报出的问题写进 `draftIssues` 一起交给作者，作者先只改这几处（2026-10-30 起，见[骨架出错只改出错的部分](27-骨架出错只改出错的部分.md)）。以前这里会丢掉草稿、只给骨架（`draft:false`），作者要从头写全图。

所以没有 `draftIssues` 的草稿一定能原样通过编译。改动或删除草稿节点时，同样在 assumptions 写「骨架调整：<key>：理由」，按[骨架偏离记录](22-试做路径搭成骨架.md#5-偏离骨架怎样记录)的规则处理。

## 6. Host 补工作流名称

create 的名称由请求定死，字段合同是 `const` 请求名称。作者重抄草稿时偶尔会漏掉 `title`（r34、r40 B、r41 B 各发生过一次），过去每次都要白花一轮修补。

现在 Host 在工具参数校验之前，按请求名称补上缺失的 `title`，并把补好的参数交给原生工具提交。其他情形不补：

- 写了别的名称：照旧退回修补；
- 修改（edit）任务：不补；
- 提交里没有 `mode: 'create'`：不补。

## 7. 什么时候不生成草稿

以下情形仍只给骨架：

- 骨架里有多个写入模块（多产物或多次写入）；
- 过程步骤需要真人审核（`requiresReview`），这需要 human 节点，Host 不代为生成；
- 没有能接到写入的数据节点。
