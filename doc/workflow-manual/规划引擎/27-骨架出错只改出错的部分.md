# 骨架出错只改出错的部分

核对日期：2026-10-30。对象：v0.0.2 T34（提交 `c135c00`）。用户决定见下文第 2 节；任务记录见[设计 Tasks T34](设计/tasks.md)。

[规划引擎索引](README.md) · [试做路径搭成骨架](22-试做路径搭成骨架.md) · [完整草稿的组装与预编译](24-完整草稿的组装与预编译.md) · [试做方法的直接接收](25-试做方法的直接接收.md)

## 1. 解决什么问题

新建工作流时，Host 把试做跑通的东西逐层交给后面的阶段：
- 试做提交的**路径**：哪几次调用组成了跑通的步骤；
- 试做提交的**方法**：分几步、每步引用哪些调用；
- Host 由路径搭出的**骨架**，以及补成的**完整草稿**。

以前这几层只要有一处不对，Host 就把整层丢掉，退回让模型从头做：
- 路径里一步的编号对不上，整条路径作废，方法跟着作废，改由模型从完整试做记录重新提炼；
- 草稿编译有一处不通过，整份草稿丢掉，作者参照骨架从头写全图。

一处小错换来一整轮重做。Desktop r56 C 就是这样：试做 2.3 分钟就跑通了，结果多花了 3.8 分钟重新提炼，作者又花 9.4 分钟从头写图。作者自写的核对代码把表头当成数据行，首跑因此失败。

## 2. 规则

2026-10-30 用户重申：“如果骨架出错了就只改骨架错误的局部部分，不要全局改。而且更改也是以试做+骨架的方式进行局部更改。”

落到实现上是三条：
1. Host 能确定怎么改的，Host 直接改，不调模型。
2. Host 不能确定的，只把出错的那一处连同试做证据和骨架交给模型，其余部分原样保留。
3. 改动要留下记录：改了哪几处、为什么改。记录放进 warnings 或诊断，随任务传给作者和最终报告。

## 3. 在哪几处生效

### 3.1 试做路径的编号对不上

试做在路径里给每一步写“第几次调用、用的什么工具”。Host 逐步核对：
- 写的编号正好是这个工具、结果也相符（成功步骤对成功调用；预期失败的检查对失败或正常返回；卡住步骤对该工具最后一次失败），就照用。
- 对不上时，Host 在上一步之后找这个工具下一次结果相符的调用，把这一步对齐过去。warnings 里写明对齐结果，如“路径编号与实际调用错位，Host 按工具名对齐：#2→#3、#3→#4”。
- 找不到任何相符调用的那一步，或者不在末尾的卡住步骤，单独去掉，warnings 写明去掉了哪几步，其余步骤保留。
- 试做方法里的引用（`cN`）和路径用的是同一套编号，Host 用同一张对照表改正，方法因此还能直接用。

r56 C 的错误正是这种：试做实际调用依次是“请求网页 → glob → 抽取 → 写入 → 回读 → 查文件状态”，路径和方法都跳过了 glob，按 1、2、3… 连续编号。现在 Host 把第 2–5 步对齐到 #3–#6，路径、方法和骨架都保留。

### 3.2 骨架草稿编译不过

Host 先用作者提交时同样的编译器和覆盖检查，把草稿提交一遍（见[第 24 篇 §5](24-完整草稿的组装与预编译.md#5-先编译再交出)）。
- 通过：照旧交给作者审核。
- 不通过：保留草稿，把这次编译报出的问题写进 `trialSkeleton.draftIssues` 一起交给作者。作者收到的指令是“先只改这几处涉及的节点、链或覆盖，其余节点原样保留，不重新设计整张图”，然后照常核对 `open` 提示。

### 3.3 试做方法没通过校验

这一处 T28 已经按同一思路做过（见[第 25 篇](25-试做方法的直接接收.md)）：试做提交的方法先当作草稿放进提炼编译器，模型只按诊断修补出错的几处，不重新提炼。现在路径编号能对齐了，方法不会再因为编号错位整份作废，能更多地直接走这条路。

## 4. 仍会整体退回的情形

只有确实没有可保留部分时，才回到原来的整体做法：
- 路径整体格式不对（不是数组、字段缺失），或者没有一步对得上实际调用：记 `TRIAL_PATH_INVALID`，按完整试做记录提炼。
- [第 24 篇 §7](24-完整草稿的组装与预编译.md#7-什么时候不生成草稿) 列出的情形：多个写入模块、需要真人审核节点、没有能接到写入的数据节点。这些情形下 Host 本来就不生成草稿，作者参照骨架写图。
