# 持久化恢复与取消

> 核对日期：2026-10-25。本文说明规划任务如何跨 Host 重启保留事实，以及取消与提交相遇时如何确定结果。

## R7 必要日志与冷恢复（R7 已安装，闭环验收暂停）

试做日志先于业务 child 启动写入；其 verified-trial 规划预览也落盘，以便保留真实执行回执和候选。普通 current-conversation 预览的内存语义不变，不能将试做日志等同于已发布 Workflow。公开事件有脱敏/限长，不保存私有思考；文件快照保存指纹与检查结果，不保存完整文件正文。

恢复重验请求/来源/回执/候选摘要及归属，活动 trial 转 interrupted；不自动重放业务或模型。原生驱动阻止持久化已知 child 冷恢复后再启动。合法 ready 预览可以读取；`visible_workflow_trial_review` 只对已完成且等待语义复核的结果重新读回，问题前后都要求文件指纹未变。needs_input 不通过该工具续跑，不完整证据不能人工豁免。源码与恢复测试见 [18](18-先执行验证再生成工作流.md)。

## 1. 哪些数据保存在哪里

默认状态目录为 `$DSH_HOME/visible-dynamic-workflows`；未设置 `DSH_HOME` 时使用 `~/.dsh/visible-dynamic-workflows`。插件配置 `stateDirectory` 可以替换该目录。

| 相对状态目录的文件 | 保存内容 | 作用 |
| --- | --- | --- |
| `planning/tasks.json` | 请求、冻结上下文、候选、状态、诊断、计数、澄清回答和事件；含 verified-trial 必要预览日志 | 恢复规划任务及审计处理过程 |
| `planning/background.json` | 后台受理身份；普通预览重启只恢复中断身份 | 防止把受理当成完成或自动重跑 |
| `trials/planning/tasks.json` | 试做规范、身份、公开事件、文件指纹/验证、人工复核及可信来源回执 | 防止重放执行，恢复实际已发生事实 |
| `library.json` | 已保存工作流及 `created` 回执 | 证明新图提交事实 |
| `editor-state.json` | 编辑草稿、修改提案及 `proposed` 回执 | 证明修改提案提交事实 |

`planning/tasks.json` 顶层是 `{ "version": 1, "tasks": [...] }`。这里的 `version: 1` 只表示内部任务记录格式，与唯一支持的工作流 JSON `formatVersion: 2`、工作流库 `schema: 2` 无关，也不意味着恢复旧工作流格式支持。

当前对话来源任务在明确发布、通过权限和 readiness 复核并进入 `publishing` 时，连同脱敏证据、方法和来源映射一起持久化；后续提交失败也可能保留该任务记录。恢复额外检查证据摘要、来源归属、步骤引用、真实节点映射及 provenanceDigest；该摘要参与来源任务的提交键。普通任务的提交身份不变。

v0.0.2 任务额外保存 engineVersion、optimization 与 optimizationDigest，包含原始基线、各轮候选、样本引用、输出摘要和比较结果；恢复及发布时重新检查报告摘要、目标、样本归属和最终候选一致性。报告不保存原始回放输入输出。无版本旧记录按 v0.0.1 读取，不自动补做优化；旧用量估计只读保留，不参与新任务准入。

任务持久化保存的是需求、结构化输出及运行控制数据，不保存规划子 Agent 的私有思考过程。它是项目本地状态，不是导入导出的工作流包。

## 2. 写入及容量边界

`PlanningStore.write()` 默认过滤普通预览任务；verified-trial 的必要日志使用显式持久化策略，再序列化、检查容量、创建临时文件、写入并 `fsync`，最后 `rename` 替换目标文件。目录创建权限为 `0700`，文件为 `0600`；规划目录和目标文件不接受符号链接。

| 限制 | 当前实现 |
| --- | --- |
| 任务数量 | 服务内最多 100 条；持久化文件也最多 100 条 |
| 文件大小 | 最多 32,000,000 字节，按序列化后的 UTF-8 字节数检查 |
| 单任务事件 | 保存最近 120 条，保留递增 `sequence`，不会因裁剪重新编号 |
| 工具返回事件 | `planningView()` 仅返回最近 8 条摘要 |
| 自动淘汰 | 写入超出条数或字节硬上限时，按创建时间清理最旧的可淘汰终态，目标降至两项上限的 75% |

2026-10-24 用户决定“自动淘汰最旧的已结束任务”。据本轮提供的 Desktop r25 验收记录，真人确认试做后，规划以 `PLANNING_FAILED：规划记录超过容量` 在 0 步失败；当时 `planning/tasks.json` 约 31.5 MB、83 条（47 published、16 failed、16 blocked、3 cancelled、1 interrupted），已发布行约 450 KB，其中模板绑定约 290 KB、冻结上下文约 134 KB。原有 32,000,000 字节／100 条硬上限没有留存清理，继续使用会永久阻断新任务。本轮未读取用户状态目录，该数据是验收输入，不是本轮重新采样。

现在 `planning/tasks.json`、`trials/planning/tasks.json` 与 `planning/background.json` 都按需清理。普通预览仍不保存正文，但计入服务内 100 条限制，并可清理已结束的内存记录。仅在超出硬上限时启动清理，目标是 24,000,000 字节且最多 75 条；保护对象过多时可以高于目标，但必须回到硬上限内。没有足够可清理记录时仍返回“规划记录超过容量”，不会删除活动任务来腾空间。排序按 `createdAt`，后台身份回执按 `acceptedAt`；时间相同按稳定插入顺序。

- 规划可淘汰终态为 `published / failed / cancelled / blocked / interrupted / returned / handed_off / conflict`；`ready / awaiting_input` 和其他活动状态不淘汰。即使已经进入终态，只要活动操作尚未退出，也受保护；本次正在写入的行始终受保护。
- 试做只淘汰已结束的 `ready / failed / cancelled / interrupted`。这里的 ready 指试做已经交给规划；`needs_input / needs_review` 仍等待真人，不能清理。
- 保留任务引用的命令交接目标、模块更新的潜在已提交来源链，以及仍待处理且缺少独立基线摘要的旧版提案所依赖的规划详情，均受保护。现代提案已有 `baseDefinitionDigest`，不依赖这份恢复详情。来源按工作流、较早版本、模块 ID／版本／实例匹配，保守保留全部匹配来源；不增加“祖先不存在就跳过”的恢复例外。若手工丢失或篡改祖先，原有完整性校验仍阻断。保护链可能使容量无法释放，此时明确报错。
- 清理先移除对应后台身份回执，再原子替换任务快照；快照提交后同步删服务 Map 和临时缓存。新快照的日志代号使旧 `tasks.journal` 无效，因此重启、后续追加或全量写入不会复活已清理详情。日志仍采用单行追加、同步落盘和分代压缩。
- `lookupReceipt` 的权威来源仍是工作流库／提案存储，本轮不改动已保存工作流或这些发布回执。留存任务的请求身份 `(workspaceId, sessionId, requestId)` 继续去重；详情及后台身份都淘汰后，这份去重历史也过期，重提同一 requestId 可能成为新任务，不能把旧请求作为无限期幂等凭证或自动重做试做。试做子任务身份识别同样以留存记录为界。
- 查询已清理 ID 返回明确的“不存在、已清理或不属于当前主对话”。试做的 `planningTaskId` 只是详情链接，已冻结的试做来源在规划上下文中自包含；规划详情被清理后，试做仍可查询并返回 `planningUnavailable`，不会重新规划、执行业务或把缺失链接当成成功。新引用已清理试做的请求明确失败。

没有新增手工清理／归档入口。发布回执还有独立容量，见[发布提案与幂等](08-发布提案与幂等.md)。

## 3. 重启先验证记录，再恢复状态

构造 `WorkflowPlanningService` 时，恢复流程不启动子 Agent：

1. 检查文件、内部格式、字段、长度、任务 ID 和请求身份是否重复。
2. 重新计算请求摘要、候选摘要及提交键，核对工作区、目标工作流、基线和修改范围。
3. 核对候选结构、就绪任务的图契约、回执归属和事件序号。
4. 将仍处于预留中的用量转入未知用量，然后根据权威提交回执恢复状态。
5. 有恢复变更时，将结果持久化一次。

篡改或损坏的数据会导致恢复拒绝，不会被自动“修正”为另一份请求。测试覆盖请求、候选、上下文、提交键及回执被修改时保留原文件。

| 重启时观察到的情况 | 恢复结果 |
| --- | --- |
| 存在匹配的权威提交回执 | 恢复为 `published`，补入回执副本，不再生成或提交 |
| 原状态是 `publishing / published`，却没有权威回执 | `blocked`，记录 `PUBLISH_UNCERTAIN`，禁止自动再次提交 |
| `ready`，尚未提交 | 保留候选；之后显式发布仍须通过权限、版本和摘要检查 |
| `awaiting_input` | 保留当前问题批次，等待原根对话回答 |
| 其他未完成状态，如排队、生成、修正、优化、回归、取消中 | `interrupted`，不自动重新调用模型 |
| 已失败、取消、冲突或阻塞，且没有提交回执 | 保留原终态 |

任务文件中的 `published` 只是状态副本；决定是否已经发布的是图或提案存储中的权威回执。恢复成功也不等于候选已执行。

### 编译检查点与无草稿纠错（2026-10-25，r28）

首次 `create/edit` 被工具 Schema 拒绝时，仅累计一次提交，不建立修复草稿。外层 `compilerDraft.document/issues` 可以保存被拒参数和诊断作为证据；草稿是否存在以 Host `checkpoint.document` 为准。无草稿检查点保持 `state=clarification`、`revision=0`、不含 `document`、`issues=[]`；提交诊断不能成为草稿修复权限。不放宽原有检查点不变量。

r28 在此后误用 `repair`，旧实现将错误写入无草稿检查点的 `issues`，触发“恢复检查点的状态与草稿不匹配”。现在返回可修复诊断 `PATCH_NO_DRAFT`，要求更正原始参数后重新提交 `create/edit`；误用同样计次，仍受原累计上限和重复失败保护约束。恢复保留已用次数及已查询模板，不自动调用模型。CLI 同样先检查当前工具 Schema，再决定拒绝参数还是建立草稿。

`if.cases[].conditions[]` 只接受 `{variable,operator,value?}`；`gte` 是 `operator` 的取值，例如 `{variable:"input.count",operator:"gte",value:"1"}`，不能另写 `gte:true`。模板说明已补充此例，条件 Schema 与运行语义不变。离线回归覆盖模板查询、Schema 拒绝、误用 repair、更正 create、原生终端及服务落盘／恢复；不代表 Desktop 或真实模型验收。

## 4. 未收到用量回执不等于没有消耗

进程中断可能发生在模型已经消耗资源、用量回执尚未送达时。恢复实际被中断的活动调用时执行：

```text
unknownUsageCalls += pendingUsageCalls
pendingUsageCalls = 0
```

因此，未收到回执的调用不会因重启被冒充为零用量。旧 `unknownTokens` / `reservedTokens` 保留原值，不改标为实际或未知 Token；终态、`ready` 和 `awaiting_input` 的用量历史不因启动而重写。恢复变更写回任务文件，下一次重启不会重复累加。实际 Token、未知调用与历史估计的区别见[资源保护与并发](07-资源保护与并发.md)。

这里恢复的是规划任务用量记录。业务工作流运行也有自己的用量记录与恢复逻辑，两类任务不能互相替代或混用取消接口。

## 5. 取消要等什么完成

`visible_workflow_plan_cancel` 先检查任务是否属于当前工作区和根对话。对于活跃任务，服务将其置为 `cancelling`、中止任务信号，并等待原处理 Promise 完成；对于尚未发布且无活跃处理的任务，直接标记 `cancelled`。

生成阶段取消后，驱动需要结束当前子 Agent，并等待清理完成。取消接口不会在子 Agent 仍未清理时提前返回“已取消”。迟到的模型候选也不会绕过取消信号继续发布。

| 取消发生的位置 | 当前行为 |
| --- | --- |
| 等待模型并发名额时 | 中止等待、释放已经取得的规划名额；尚未启动子 Agent 时不增加尝试次数 |
| 子 Agent 正在生成时 | 等待驱动清理，再确定任务终态 |
| Graphon 片段回归进行中 | 中止回放、等待 Runtime/Graphon 清理并删除临时记录；不返回成功验证 |
| 子 Agent 清理失败 | 优先进入 `blocked`，诊断为 `PLANNER_CLEANUP_FAILED`，不能伪装成干净取消 |
| 等待用户回答或预览候选已就绪 | 标记取消；不会提交或执行工作流 |
| 图或提案已经原子提交 | 保留 `published` 和回执，取消不会回滚已发生的提交 |
| 任务已是终态 | 返回现有结果；若仍有收尾 Promise，先等待其结束 |

Host 关闭时，`close()` 中止生命周期信号，并等待活跃任务结束及用量记录完成。异常退出则依靠下一次启动执行前述恢复规则。子 Agent 的 `dispose` 边界见[子 Agent 生命周期与工具隔离](05-子Agent生命周期与工具隔离.md)。

## 6. 预览任务为什么重启后消失

`preview: true` 的任务、澄清和取消全部保存在内存，不创建规划记录文件，也不把预览任务混入其他任务的持久化结果。只读或规划模式从工具入口强制使用预览。

预览生成成功后停在 `ready`。用户显式要求保存时，发布接口校验原根对话、可写权限、最新任务版本和候选摘要，再转入持久化发布流程。发布前就被权限检查拒绝的预览仍不落盘。

Graphon 局部回归需要在临时目录建立隔离运行存储，并在结束后删除；这不改变上述“预览任务和用户工作流不落盘”的边界，也不能误写成整个进程绝对不创建任何临时文件。

Host 重启后无法从磁盘找回未发布预览，需重新发起请求。普通已持久化任务则可恢复查询，但当前没有自动续跑中断任务的工具；需要继续生成时应发起新的规划请求。

## 局部编辑协议的恢复边界

局部编辑只用于新模型调用。Host 编译后的 canonical PlannerOutput 和完整候选继续使用原持久化合同；旧 graphJson 任务通过原读取解析器恢复，不会被当成新编辑操作重放。修正用的可信草稿由 Host 检查点保存；恢复重新核对任务归属、Schema／合同、累计次数及当前修复权限。外层 `compilerDraft` 的被拒参数记录不是修复草稿；重启不自动续跑。详见 [17](17-局部编辑意图与宿主编译.md)。
