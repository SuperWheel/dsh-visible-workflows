# 修改先定位再回放

核对日期：2026-10-30。对象：v0.0.2 T37。用户决定见下文第 2 节；任务记录见[设计 Tasks T37](设计/tasks.md)。

[规划引擎索引](README.md) · [骨架出错只改出错的部分](27-骨架出错只改出错的部分.md) · [试做路径搭成骨架](22-试做路径搭成骨架.md)

## 1. 解决什么问题

修改已保存的工作流时，真正提交修改只要一瞬间。Desktop r61 E（给「T18 CSV 统计 r55」的表格加一列「扩展名」）里，Host 编译只用了 0.4 秒，全程却要 9.6 分钟。其中约 6 分钟是主对话自己摸底：
- 找工作流：清单返回约 5 万字，溢出成文件，主对话再用 grep、bash 去读；
- 找节点：读了两次节点，又读工具说明；
- 看数据：自己调用一次「文件信息」工具，才知道上游每行只有 `name / bytes / lines / lineEnding`，没有扩展名；
- 想办法：用 143 秒想明白「模板过滤器取不出扩展名，要加 code 节点」。

这几件事 Host 不用模型就知道：
- 工作流的标题就写在需求里；
- 「字节数」三个字只出现在模板节点里；
- 这个工作流跑过一次，每个节点的真实输出都在运行记录里。

## 2. 规则

2026-10-30 用户批准 T37，并补充：「如果这个流程之前没有执行记录的话，直接执行一次就行。」

落到实现上是两条：
1. **先定位。** Host 用一次调用把目标、目标周围的真实数据和绑好的链段交给主对话，主对话只负责写修改。执行由 Host 做，不让主对话跟着走一遍：主对话每走一步都是一次模型调用。
2. **再回放。** 修改编译通过后，Host 用这次运行的真实数据只重跑改动的节点，跑通了才生成提案；不通过就只改失败的那个节点（同[第 27 篇](27-骨架出错只改出错的部分.md)）。

## 3. 定位：`visible_workflow_locate`

主对话传两样东西：`workflow`（用户说的标题或工作流 ID）和 `request`（用户原话）。Host 返回：

| 内容 | 怎么来的 |
| --- | --- |
| 目标工作流和版本 | 先按 ID 精确匹配，再按标题精确匹配，最后按包含匹配；对不上或有多个时只返回候选，请用户选 |
| 目标节点 | 原话引号里的文字（去掉工作流标题本身），出现在哪些节点的标题或配置里；原话直接写了节点标题的也算。格式与 `visible_workflow_nodes` 相同；在链段里的目标带它的别名 `alias`，没有 `alias` 的在链段外（见第 5 节） |
| 真实输出样例 | 目标节点和它按 ID 读取的上游节点，在最近一次运行里的输出：数组取前 3 项，长文字截到 1200 字，去掉和解析结果重复的 JSON 文本 |
| 链段 | 以目标为锚的别名清单 `chainNodes` 和 code 模板 `codeTemplate`。绑定字段（版本、基线校验串、链前缀、锚点、作用域、边界）不交给主对话，Host 按「对话 + 工作流」记住，见第 4 节 |
| 下一步 | 样例里已有的字段直接 `update` 目标；没有的字段在目标前 `insert` 一个 code 节点，再 `update` 目标改读新 key |

最近一次运行优先取当前版本的，再取最新的；没有任何节点结果的运行不算。

**没有运行记录时**，Host 直接执行一次工作流（用户决定），最多等 180 秒，再用这次运行的结果。两种情况例外：
- 工作流需要必填输入：Host 不替用户填，样例为空，并说明原因；
- 180 秒内没跑完：只用已完成节点的结果，运行在后台继续。

同一版本只自动执行一次（请求 ID 为 `locate-<工作流ID>-<版本>`），再次定位直接复用这次运行。

## 4. 回放：splice 之前先跑一遍改动的节点

定位之后，`visible_workflow_splice` 的 `chain` 只写 `operations`（需要时加 `exports`）。缺的绑定字段由 Host 用本对话最近一次定位这个工作流时记下的绑定补齐；主对话自己写了的字段照用，照常校验。工作流版本已经变了、或者本对话没定位过这个工作流时不补，照旧按缺字段退回。r62、r63 E 里主对话照抄绑定字段，一次多抄了别名清单，一次漏了锚点，各被退回一次。

Host 先在本地编译同一个 chain，得到候选图，再调用 `WorkflowRuntime.replay`：
- 回放范围：候选图里新增或改了配置的节点，以及按 ID 读取它们的下游节点。没被改动、也不读改动节点的节点不碰。
- 只跑纯计算节点：code、模板、列表、聚合、输出。遇到工具、Agent、模型、HTTP 等有副作用或要调模型的节点就停在这里，标为「接受后运行时执行」，读它的下游节点不再列出。
- 输入：上游节点直接用运行记录里的输出；输入变量、环境变量、系统变量也取自这次运行。
- 不留痕迹：回放用的运行副本从不保存，运行列表里不会多出记录，原运行的节点结果也不改。

结果随 splice 返回在 `replay` 里：每个节点的状态（`success`、`failed`、`not-replayed`）、输出样例或错误。
- 有节点失败：返回 `state: replay-failed`，不建规划任务、不生成提案。主对话只改失败的节点，用同一个 chain 重新提交。
- 全部通过或只有不回放的节点：照常生成提案，`replay` 附在返回里，由主对话向用户汇报。
- 编译本身不通过、找不到运行记录、或者没有节点被改动时不回放，交给原来的规划入口报错或照常处理。

## 5. 顺带修的几处

- `visible_workflow_list` 只返回 ID、标题、版本、作用范围、节点数、更新时间和简短描述，不再带整张图。要完整定义用 `visible_workflow_get`。
- 对象类参数（如 splice 的 `chain`）收到 JSON 文本时，Host 自己解析。r61 E 主对话就因为把 chain 写成字符串被退回过一次。
- splice 的 `chain` 里混进定位包的 `chainNodes`、`chainRules`、`codeTemplate` 时，Host 直接丢掉这几个只读字段。r62 E 主对话把它们一起塞进了 chain，被退回一次。其他未知字段照旧退回。
- insert 或 replace 把新节点的 `key`、`template`、`values`、`title` 直接写在操作上、没放进 `nodes` 时，Host 把它们收成一个节点。r64 E 主对话这样写，被退回一次。操作上同时有 `nodes`、或缺 `key`／`template` 时不猜，照旧退回。

## 5.1 一个需求只交一个提案

链段只能是一段连续、不分叉的顺序节点。Desktop r65 E 改「T18 CSV 统计 r53」时，定位找到两个目标：表格模板和一个逐字核对表头的代码节点。核对节点在条件分支后面，不在链段里，主对话没法在同一次 splice 里改它，就另用 `visible_workflow_edit` 交了第二个提案。两个提案都基于 v1，接受一个后另一个就失效，主对话却告诉用户两个都接受。T37.7 的处理：

- **链段外的节点也用 update。** `update` 的 `target` 可以写节点的 key（如 `n9`）或节点 ID。节点在链段里时等同于它的别名；在链段外时 Host 就地合并字段，不碰连线，和链段的改动编译成同一个候选，回放也一起覆盖。insert、replace、delete 仍只认链段别名。链段外节点不能整体改 `body`，受 `targetNodeIds` 授权范围和固定节点保护约束。编译时只提交 update 写到的字段，以及读了被删节点、需要改写引用的字段；其余字段原样保留。r53 的核对节点 `inputs` 读了写入模块内部的回读结果，若整份配置一起提交，会被模块保护拒绝（「模块内部引用不可见」）。
- **同一版本只留一个提案。** 同一个对话已经在某个工作流的某个版本上交过修改，而那次的任务还在生成、或者生成的提案还没被处理，再交一个不同 `request_id` 的修改时，Host 退回 `REVISION_PENDING`，说明「同一版本的提案只能接受一个」，让主对话如实告诉用户先接受或拒绝前一个。splice 在回放之前就检查，edit 和 plan 在建任务之前检查。用同一个 `request_id` 重交不算第二个；前一个失败、取消或提案已被拒绝时不拦。
- **两处小修。** 所有操作都没写 `draftRevision` 时，Host 按给出的顺序补 0、1、2…，只写了一部分时照旧退回。`chain` 写成 JSON 文本又解析失败时，报错带上出错位置附近的文字，并提示直接传对象，不用自己转义。
