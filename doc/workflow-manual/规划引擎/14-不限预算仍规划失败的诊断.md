# 不限预算仍规划失败的诊断

> 2026-10-21 说明：工作流预算系统已于 2026-10-20 移除（见 [S12](设计/tasks-规划提速与上下文复用.md)）。本文涉及预算问答、额度、增额或费用的内容仅为历史记录，不再执行；Token 用量只作性能计量保留。

核对日期：2026-10-18。范围：用户提供的 GitHub Top10 工作流三次规划失败、对应子会话和实际安装包，以及所有本地预算触发路径。第 1–5 节保留修复前审计事实；第 6 节起记录本次修复与验收，当前规则以[资源保护与并发](07-资源保护与并发.md)为准。

## 1、结论

用户两次均选择了 `budgetDecision.mode = unlimited`，冻结的 `executionPolicy` 都是 `{}`，选择被正确保存。第一次被规划引擎的固定估算额度拒绝；第二次被规划子 Agent 的 180 秒总期限中止。没有候选产出，尚未进入 Graphon 执行，因此这两次失败不是业务工作流运行耗尽预算。

当前实现将用户执行用量限制、规划内部资源保护、模型输出上限混在“预算”概念下，错误提示又没有明确具体触发项。仅提高用户填写的总 Token 数不能修复本次问题。

### 2.1、第一次在第二步准入前失败

16:10:18.014 子任务启动，16:12:13.979 首步用量结算。随后完成六个精确目录查询：`http`、`code`、`input`、`output`、`template`、`builtin:time.now`，均成功，返回内容序列化合计 10,635 UTF-8 字节。16:12:14.049 任务失败，第二个模型步骤没有开始。

该任务只用了一个子任务、一个模型步骤，未命中 8 子任务或 24 步限制；没有未知占用。按已核对的准入代码，下一步被拒绝的条件是：

```text
11,010 已知 Token + 下一步输入估计（实际是 UTF-8 字节数）+ 8,192 输出预留 > 64,000
```

因此，本次下一步输入估计超过 44,798 字节即可触发失败。这是根据代码和任务计数推导的阈值；失败日志没有保存该步具体输入估计，不能将阈值写成精确请求大小或真实 Token 数。不是已消耗 64,000 Token，也没有证据显示供应商账户余额不足。

### 2.2、第二次在持续输出时被总期限取消

16:12:54.355 进入生成阶段，16:12:54.404 子任务启动。首步耗时约 104 秒，16:14:38.435 第二步获准开始。第二步最后一个记录到的流事件是 16:15:54.318；16:15:54.380 消息被标为 `interrupted`；16:15:54.416 任务以超时失败。

从生成阶段开始到失败约 180.061 秒，最后流事件距中断约 62 毫秒。证据支持“仍有模型输出时被固定总期限取消”，不支持“模型长时间无响应”。180 秒覆盖整个子任务的多次模型请求和工具交互，并非每次请求各有 180 秒。

第二步没有完整用量回执，原预留 51,958 转为未知占用。不能据此声称额外消耗了 51,958 Token，也不能把它当成零。第二次是新 requestId、新账本，没有继承第一次的已知消耗。

| 问题 | 当前实现 | 影响 / 来源 |

| 两套限制独立 | “不限”只清除工作流执行的 `tokenBudget`、`perTaskTokens`、`maxAgentTasks` | 规划仍有固定 64,000 门槛；见 [creation-budget.ts](../../../src/host/creation-budget.ts) 的 `applyCreationBudget`、[service.ts](../../../src/host/planning/service.ts) 的 `MAX_TOKENS` / `invoke` |

| 失败码含混 | 用量估计拒绝与步数 / 子任务耗尽共用 `BUDGET_EXHAUSTED`；超时与其他错误共用 `PLANNING_FAILED` | 缺少具体限制、当前数值和恢复建议；见 `service.ts` 的 `fail` |
| 预留与输出上限耦合 | 问答称单次预留“不代表模型输出上限”，运行时却将 `reservation.tokens` 传为 `maxTokens` | 独立发现，并非这两次规划失败的直接原因；见 [creation-budget.ts](../../../src/host/creation-budget.ts)、[runtime.ts](../../../src/host/runtime.ts) 的 `metered` / `modelCall`、[llm.ts](../../../src/host/llm.ts)、[native-agent.ts](../../../src/host/native-agent.ts) |

正常用量回执路径未发现重复累计：逐步结算会释放对应预留，已有逐步回执时不再加聚合值，取消时只将未结算部分转为未知。实际重复输入可能产生新的模型用量，但这不同于账本把同一回执重复相加。

## 4、推荐调整

Token 可用于描述模型上下文和调用用量，但总 Token 数不能直接等同于跨模型费用。当前系统没有价格表、币种账本或完整输入 / 输出 / 缓存分类计费，不应宣称金额预算控制。

表 3：建议的保留与简化边界，均尚未实施。

| 控制项 | 推荐 | 具体处理 |
| --- | --- | --- |
| 隐藏的 64,000 混合估算额度 | ✅ 取消作为默认用量硬门槛 | 字节体积保护单独命名；按模型能力判断上下文，不能简单把字节除以固定系数假装精确 Token |
| 用户主动设置的总 Token 上限 | ✅ 高级选项，默认不限 | 名称改为“用量上限”，明确规划 / 运行作用域；不包装为费用金额 |
| 每次调用预留 Token 问答 | ✅ 从普通预算问答移除 | 系统处理预留，模型输出上限独立配置并尊重模型能力 |
| 单子任务固定 180 秒 | ✅ 改造 | 区分请求无进展超时与任务总期限；持续有进展时避免用短总期限直接丢弃工作，达到总保护阈值时保留可恢复状态并明确询问继续 |
| 4 步 / 24 步 / 8 子任务限制 | ✅ 保留有界保护，重新设定策略 | 不全删；拆分错误码，支持受控继续，避免正常查目录后被低步数阻断 |
| 并发、队列、取消、权限、输出校验 | ✅ 保留 | 这些约束分别保护资源、授权与图正确性，不归入费用预算 |
| 用量未知 | ✅ 保留未知状态 | 不伪造为零或真实花费；只有用户启用明确用量上限时，才用于该限制的保守准入决策 |
| 金额预算 | ✅ 暂不伪造 | 只有取得可靠模型价格、计费分类与用量后才考虑实现 |

既有“同一对话同一工作流只问一次，明确修改才重问”的规则，本轮不变更。简化字段不等于取消已明确设置的额度，更不能擅自更换用户模型或降低推理强度。

建议实施顺序：先拆分诊断与估算单位；再移除默认估算额度阻断、解耦预留和输出限制；随后改造超时与受控继续。目录查询保持精确按需返回，防止未来全量查询膨胀。验收应覆盖“首步已结算后继续”“超过 180 秒仍有进展”“真实无响应取消”“显式用量上限”“未知回执”及原会话预算规则。

## 7、为什么有引擎仍可能不懂字段

这是独立的说明缺口，被规划失败放大了：

1. 原子 Agent 目录给出了节点配置 schema，但大量字段只有类型、没有含义。此次七个节点的 input/output/tool/template/iteration schema 均无 description；code/llm 各只有一处。目录还缺少真实输出路径、配置示例、节点选择说明。
2. 主 Agent 只有节点种类列表及少量引用说明，没有节点语义查询工具。预算失败后 child 没有提交候选，主 Agent 转而猜测 JSON 并调用 glob/grep 查源码。相关主会话中确有自行回退的表述，但没有真正调用 `visible_workflow_save`，不能说错误图已保存。
3. 所以解除预算误报不能自动补齐字段知识。现增加主 Agent 与 child 共用的[语义词典](15-Agent工作流语义词典.md)，按需提供字段、输出、例子和当前 schema；保存工具与主提示统一禁止自然语言生成失败后自行绕过规划器。

词典不能保证模型永不犯错；候选仍经过当前 JSON 校验、真实目录核对、稳定引用和作用域检查，再由 readiness 给出执行前待配置项。

### 7.1、真实模型验收发现的词典传输问题

安装后的真实子 Agent 在前三次合法的 `includeSchema:true` 查询中收到 `INVALID_TOOL_OUTPUT: value is not lossless JSON`。原因是 Zod 4.4.3 的 `toJSONSchema()` 返回值带有不可枚举的 `~standard` 私有属性；主工具返回字符串时不会暴露它，子 Agent 直接返回对象时却会被 DSH 的严格 JSON 快照拒绝。关闭 Schema 后模型可以继续查询，但不能据此认为接口没有问题。

已在共享节点目录输出边界将 Schema 转为纯 JSON 文档，保留所有可序列化的字段规范。回归直接使用 DSH 工具依赖的 `snapshotJsonValue`，覆盖 20 类节点及实测失败的两组查询。这个缺陷与预算计算分开修复，避免查询失败额外消耗规划轮次。

## 8、修复覆盖矩阵

| 场景 | 修复后的处理 | 是否保留阻断 |
| --- | --- | --- |
| 规划下一轮输入字节 + 已报告 Token 超过旧 64k | 删除混合门槛，分别记录字节和实际用量 | 否 |
| 规划缺失 usage、取消、子任务失败后重试 | 保留未知调用与已知回执；未知不是零，也不占虚构 Token 额度 | 不因估算阻断 |
| 规划默认 8,192 输出额度 | 沿用宿主当前模型默认值，去掉规划器自定输出截断 | 保留供应商实际限制 |
| 高强度模型持续输出超过 180 秒 | 移除旧短总期限，用进展事件刷新无响应计时 | 5 分钟无进展或 20 分钟处理段仍停止 |
| 多次目录查询、修复或反推累计步骤 | 单 child 8 步、任务 24 步/8 child，候选 3 次等有限保护 | 是，明确为循环/次数保护 |
| 上下文或结构化结果过大 | 输入与输出各 2 MB 体积保护；不静默截断 | 是，明确为字节体积 |
| 供应商上下文、余额、配额或限流错误 | 使用真实错误类别，不称为本地执行预算不足 | 是，不能绕过供应商 |
| 业务运行不限却到 100 个 Agent 任务 | 删除默认任务总数门槛 | 仅显式 maxAgentTasks 生效 |
| 业务模型、原生 Agent、修复使用默认 4,096 预留 | 预留只用于调度，不作为模型输出上限 | 不因默认预留截断 |
| 显式设置运行总 Token 或任务数 | 继续核对已报告用量、在途与未知记录 | 是，用户选择有效 |
| 原生 Agent 已执行工具后触达显式额度 | 明确中途停止，不置为可自动重跑的 pending | 保留执行事实，恢复需审核 |
| SDK 同一步请求错误后自动重试 | 在 request-error 重试边界再次核对累计回执，不能跳过准入 | 显式额度或未知回执仍生效 |
| 用户取消、权限拒绝、清理失败或候选不合法 | 保持对应错误和清理语义 | 是，不包装成预算不足 |
| 普通预算问答 | 只问是否设运行用量上限，选择设置后填写总量 | 同工作流同对话只问一次 |

以上移除的是隐藏或单位错误的限制，不会清除用户已明确设置的当前运行策略，不改变 JSON 唯一标准、Graphon、权限、Secret 及发布提案边界。Token 总数只是用量口径，未实现也不伪造金额计费。
